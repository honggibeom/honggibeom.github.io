> 프론트엔드 빌드 도구 시리즈 2편. 1편에서 빌드 도구 층을 봤다면, 이번엔 그 위에 얹히는 층이다.

## 왜 다시 서버로 갔나

2015년부터 한동안 방향은 명확했다. **전부 클라이언트로 옮기자.** 서버는 JSON만 주고, 화면은 브라우저에서 React가 그린다. 페이지 이동에 새로고침이 없고, 백엔드와 프론트엔드가 깔끔하게 분리된다.

그런데 대가가 따라왔다.

- **첫 화면이 늦다.** HTML은 `<div id="root"></div>` 한 줄이고, JS 번들을 전부 받아서 실행해야 뭔가 보인다
- **번들이 계속 커진다.** 기능을 넣을수록 사용자가 받아야 할 JS가 늘어난다
- **SEO와 공유가 곤란하다.** 크롤러와 링크 미리보기가 빈 HTML을 본다
- **데이터 폭포가 생긴다.** JS 로드 → 렌더 → API 요청 → 다시 렌더. 요청이 컴포넌트 안에 있으면 이게 중첩된다
- **느린 기기에서 특히 나쁘다.** JS 파싱과 실행은 CPU를 쓴다. 저가 안드로이드에서 체감 차이가 크다

메타 프레임워크는 이 문제들에 대한 답으로 나왔다. **"서버에서 할 수 있는 건 서버에서 하자"**가 공통된 방향이고, 프레임워크마다 그 방법이 다르다. 그 차이를 이해하는 게 이 글의 목적이다.

## 렌더링 방식 사전

이름이 많아 보이지만 축은 두 개뿐이다. **HTML을 언제 만드는가**, 그리고 **만든 뒤 JS로 무엇을 하는가**.

### CSR (Client-Side Rendering)

```
서버 → 빈 HTML + JS 번들
브라우저 → JS 실행 → DOM 생성 → API 호출 → 화면
```

전통적인 SPA다. CRA로 만든 앱, 그리고 이 블로그가 여기 해당한다. 서버가 필요 없어서 정적 호스팅(GitHub Pages 같은)에 올릴 수 있다는 게 가장 큰 장점이다.

### SSR (Server-Side Rendering)

```
서버 → 요청마다 컴포넌트 실행 → 완성된 HTML
브라우저 → HTML 즉시 표시 → JS 받아서 하이드레이션 → 인터랙션 가능
```

첫 화면이 빠르고 SEO가 된다. 대신 요청마다 서버가 렌더링하므로 **서버가 필요하고 비용이 든다.**

### SSG (Static Site Generation)

```
빌드 시점 → 모든 페이지의 HTML을 미리 생성
요청 시    → 그냥 파일 전달 (CDN)
```

가장 빠르고 가장 싸다. 대신 **내용이 바뀌면 다시 빌드해야 한다.** 페이지가 10만 개면 빌드가 몇십 분씩 걸린다.

### ISR (Incremental Static Regeneration)

SSG와 SSR의 절충. 정적으로 만들어두되 일정 시간이 지나면 백그라운드에서 다시 만든다. 사용자는 항상 캐시된 페이지를 즉시 받고, 갱신은 뒤에서 일어난다. 커머스 상품 페이지처럼 **자주 바뀌지만 실시간일 필요는 없는** 것에 맞는다.

### 스트리밍 SSR

SSR의 문제는 **가장 느린 데이터 하나가 전체를 막는다**는 것이다. 페이지에 추천 목록이 있고 그게 2초 걸리면, 나머지가 준비돼도 2초 뒤에 HTML이 나간다.

스트리밍은 준비된 부분부터 먼저 보낸다.

```
0.1초: 헤더, 사이드바, 본문 HTML 전송 + 추천 자리에 스켈레톤
2.0초: 추천 목록 HTML을 이어서 전송 → 스켈레톤 자리에 채워짐
```

React의 `<Suspense>`가 이 경계를 표시하는 도구다.

### PPR (Partial Pre-Rendering)

한 페이지 안에서 **정적인 부분과 동적인 부분을 나눈다.** 껍데기(레이아웃, 네비게이션, 상품 설명)는 빌드 시점에 만들어 CDN에서 즉시 주고, 개인화된 부분(장바구니 개수, 추천)만 요청 시점에 스트리밍으로 채운다.

"이 페이지는 정적이냐 동적이냐"라는 이분법을 없앤 것이 핵심이다. Next.js가 이 방향을 Cache Components라는 이름으로 정리했다.

### 아일랜드 (Islands)

Astro가 대중화한 방식이다. **기본은 순수 HTML, 인터랙션이 필요한 컴포넌트만 섬처럼 따로 하이드레이션한다.**

```
[ 정적 HTML — JS 0 ]
   헤더 · 본문 · 푸터

   ┌──────────────┐  ← 이 섬만 JS 를 받고 하이드레이션
   │ 검색 자동완성 │
   └──────────────┘

   ┌──────────────┐  ← 이 섬은 화면에 보일 때 로드
   │ 댓글 위젯     │
   └──────────────┘
```

블로그나 문서 사이트는 화면의 95%가 그냥 텍스트다. 그 95%에 JS를 보낼 이유가 없다는 게 아이디어다. 섬마다 로드 시점을 따로 정할 수 있다(즉시 / 유휴 시간 / 화면에 보일 때 / 특정 화면 크기에서만).

### 리주머빌리티 (Resumability)

Qwik의 방식이고, 아일랜드보다 한 걸음 더 간다. 아일랜드도 각 섬은 결국 하이드레이션을 한다. Qwik은 **하이드레이션 자체를 없앤다.**

서버가 렌더링하면서 **실행 상태와 이벤트 리스너 정보를 HTML 안에 직렬화해 넣는다.** 브라우저는 아무것도 재실행하지 않고, 사용자가 버튼을 누르는 순간에야 그 버튼에 필요한 코드 조각만 받아 온다. 이론상 초기 JS가 거의 0이다.

### 정리

| 방식 | HTML 생성 시점 | 초기 JS | 서버 필요 | 잘 맞는 곳 |
| --- | --- | --- | --- | --- |
| CSR | 브라우저 | 전체 | 아니오 | 로그인 뒤 대시보드, 사내 툴 |
| SSG | 빌드 시점 | 전체(하이드레이션) | 아니오 | 문서, 마케팅 페이지 |
| SSR | 요청마다 | 전체(하이드레이션) | 예 | 개인화된 콘텐츠 |
| ISR | 빌드 + 주기적 갱신 | 전체 | 예 | 커머스 상품 목록 |
| 스트리밍 SSR | 요청마다(분할 전송) | 전체 | 예 | 느린 데이터가 섞인 페이지 |
| PPR | 빌드 + 요청 시 채움 | 전체 | 예 | 껍데기는 같고 일부만 개인화 |
| 아일랜드 | 빌드 또는 요청 | **섬만** | 선택 | 콘텐츠 중심 사이트 |
| 리주머빌리티 | 요청 | **거의 0** | 예 | 읽기 위주, 인터랙션 드문 사이트 |

## 하이드레이션이라는 비용

SSR/SSG에서 계속 나오는 이 단어를 짚고 가야 한다.

서버가 HTML을 만들어 보내면 화면은 보인다. 하지만 그건 **그림**이다. 버튼을 눌러도 아무 일이 없다. 이벤트 핸들러가 붙어 있지 않기 때문이다.

그래서 브라우저가 JS를 받아서 **같은 컴포넌트 트리를 한 번 더 만들고, 서버가 만든 DOM과 맞춰본 뒤, 이벤트 핸들러를 붙인다.** 이게 하이드레이션이다.

여기서 두 가지 문제가 나온다.

1. **같은 일을 두 번 한다.** 서버에서 렌더링하고 클라이언트에서 또 렌더링한다
2. **"보이는데 안 눌리는" 구간이 생긴다.** HTML이 뜬 시점부터 하이드레이션이 끝날 때까지, 사용자는 다 된 화면을 보면서 아무것도 못 한다. 이걸 **uncanny valley**라고 부른다

게다가 하이드레이션을 하려면 **결국 그 컴포넌트의 JS를 전부 받아야 한다.** SSR을 붙여도 번들 크기 문제는 그대로 남는다는 뜻이다.

2020년대 프레임워크 경쟁의 상당 부분이 **이 비용을 어떻게 줄이느냐**의 싸움이다. 아일랜드는 하이드레이션 범위를 줄이고, 리주머빌리티는 아예 없애고, RSC는 클라이언트로 갈 코드 자체를 줄인다.

## RSC — SSR과 뭐가 다른가

React Server Components는 가장 많이 오해받는 개념이다. **"서버에서 렌더링한다"는 점이 SSR과 같아 보이지만 목적이 다르다.**

| | SSR | RSC |
| --- | --- | --- |
| 목적 | 첫 화면 HTML을 빨리 주기 | **클라이언트 번들에서 코드를 빼기** |
| 컴포넌트 JS | 클라이언트로 간다 (하이드레이션 필요) | **클라이언트로 가지 않는다** |
| 실행 시점 | 요청마다 서버에서 1회 + 클라이언트에서 1회 | **서버에서만** |
| 상태·이벤트 | 가질 수 있다 | 가질 수 없다 |

서버 컴포넌트는 서버에서 실행되고, 그 **결과**(직렬화된 UI 트리)만 클라이언트로 간다. 컴포넌트 코드 자체는 번들에 들어가지 않는다.

```jsx
// 서버 컴포넌트 — 기본값 (Next.js App Router)
// 이 파일의 코드도, markdown 라이브러리도 클라이언트 번들에 안 들어간다
import { renderMarkdown } from "heavy-markdown-lib";

export default async function Post({ id }) {
  const post = await db.post.findById(id);   // DB 를 직접 호출한다
  return <article>{renderMarkdown(post.body)}</article>;
}
```

```jsx
"use client";   // 여기서부터 클라이언트. 이 경계 아래는 번들에 들어간다

export function LikeButton({ initial }) {
  const [n, setN] = useState(initial);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
```

`"use client"`가 **경계선**이다. 그 위는 서버, 아래는 클라이언트. 무거운 라이브러리(마크다운 파서, 날짜 포맷터, 구문 강조기)를 서버 쪽에 두면 사용자는 그걸 다운로드하지 않는다.

대가도 분명하다. 서버와 클라이언트의 경계를 늘 의식해야 하고(`useState`를 쓰려면 `"use client"`, 그러면 그 아래 전부가 번들에 들어간다), 서버 런타임이 필요하고, 디버깅이 어려워진다. **2026년 현재 RSC는 표준이 아니라 React 진영의 한 선택지다.** 아래에서 보듯 그 반대 방향으로 간 프레임워크도 있다.

## 프레임워크별로

### Next.js — 사실상의 기본값

2026년 8월 기준 최신은 **16.3**이고, 메이저 16은 2025년 10월에 나왔다.

- **Turbopack이 dev/build 모두 기본 번들러**가 됐다. webpack으로 돌아가려면 `--webpack`
- **Cache Components** — `"use cache"` 지시자 기반의 새 캐싱 모델. 예전 App Router의 암묵적 캐싱이 혼란스러웠던 걸 정리해서, **기본은 전부 요청 시점 실행이고 캐싱은 명시적으로 opt-in**하는 방향으로 뒤집었다. 실험적이던 PPR 플래그는 이 모델로 흡수되며 제거됐다
- `middleware.ts`가 `proxy.ts`로 이름이 바뀌었다(기존은 deprecated)
- React 19.2 기반. View Transitions, `<Activity>`, `useEffectEvent` 사용 가능
- `next lint`가 제거됐다. ESLint나 Biome을 직접 쓴다

**가장 강한 것**: 필요한 렌더링 방식이 전부 있고(SSG/SSR/ISR/PPR), 생태계와 채용 시장이 가장 크고, Vercel 배포가 매끄럽다.

**약한 것**: 복잡도. 캐싱 모델이 버전마다 바뀌어서 "이게 지금 캐시되는 건가"를 계속 확인하게 된다. Vercel 밖에 배포하면 손이 더 간다.

### Nuxt — Vue 진영의 Next.js

**4.5**가 최신(2026년 7월)이고, Nuxt 3는 2026년 7월 말로 지원이 끝났다.

- 내부 빌드는 **Vite 8**(Rolldown 기반). Rspack도 선택 가능
- **Nitro**가 특징이다. Nuxt와 별개로 존재하는 서버 엔진인데, 같은 코드를 Node·Cloudflare Workers·Vercel·Deno 등 여러 배포 타깃으로 어댑터만 바꿔서 내보낸다. 배포처에 덜 묶인다는 게 Next.js와 비교되는 지점이다
- 라우트 단위 하이브리드 렌더링(이 경로는 정적, 저 경로는 SSR)이 설정 한 곳에서 된다

**가장 강한 것**: 자동 임포트와 파일 기반 규칙이 촘촘해서 보일러플레이트가 적다. 배포 유연성.

### SvelteKit — 컴파일러가 런타임을 지운다

SvelteKit 2.7x / Svelte 5.5x가 현재 라인이다. Svelte 6는 아직 없다.

Svelte의 접근은 다르다. **가상 DOM이 없다.** 컴파일 시점에 "이 값이 바뀌면 이 DOM 노드를 이렇게 고친다"는 코드를 직접 생성한다. 그래서 런타임으로 딸려가는 프레임워크 코드가 적고 번들이 작다.

Svelte 5의 **runes**(`$state`, `$derived`, `$effect`)가 반응성 모델을 명시적으로 바꿨고, 이제 이게 표준이다.

**가장 강한 것**: 번들 크기와 코드량. 같은 화면을 만들 때 쓰는 줄 수가 눈에 띄게 적다.

**약한 것**: 생태계 규모와 채용 시장이 React보다 작다.

### Astro — 콘텐츠 사이트라면 여기부터

**Astro 6**이 2026년 3월에 나왔다. Vite 위에서 돈다.

- **아일랜드**가 기본 모델이다. 기본 출력은 JS 0
- **React, Vue, Svelte, Solid 컴포넌트를 한 프로젝트에서 섞어 쓸 수 있다.** 각 섬이 자기 프레임워크를 쓴다
- **Server Islands** — 정적 껍데기 안에 서버 렌더링된 섬을 스트리밍으로 끼워 넣는다. 페이지는 CDN에서 즉시 오고 개인화 영역만 뒤늦게 채워진다
- **Content Layer** — 마크다운/CMS/API를 같은 방식으로 다루는 콘텐츠 API. Astro 6부터는 이게 유일한 방식이고 예전 방식은 제거됐다

**가장 강한 것**: 블로그, 문서, 마케팅 사이트. State of JS 2025에서 메타 프레임워크 중 만족도 1위였다.

**약한 것**: 화면 대부분이 인터랙티브한 앱(대시보드, 에디터)에는 안 맞는다. 그건 애초에 대상이 아니다.

### React Router v7 — Remix가 여기로 왔다

Remix와 React Router가 합쳐졌다. **Remix의 프레임워크 기능이 React Router v7에 흡수됐고**, 지금 React Router v7이 그 자리를 잇는다. Vite 기반이다.

React 팀이 CRA 대신 권하는 두 선택지 중 하나가 이것이다. Next.js보다 얇고, 웹 표준(`Request`/`Response`/`FormData`)에 가깝게 설계돼 있다.

여기서 흥미로운 사건이 하나 있다. **Remix v3는 React를 버렸다.** Preact 포크 위에서 훅 대신 명령형 API를 쓰는, 웹 표준 중심의 완전히 새로운 것으로 다시 쓰이고 있다(2026년 8월 기준 아직 정식 출시는 아니다). RSC로 몰려가는 흐름에서 정반대로 걸어나간 유일한 사례라 눈여겨볼 만하다.

### TanStack Start — 클라이언트 우선의 대안

TanStack Router/Query 팀이 만든 풀스택 React 프레임워크. Vite 기반이고, 2025년 9월 1.0 RC를 거쳐 현재 1.x가 활발히 나오고 있다.

특징은 **타입 안전성**과 **클라이언트 우선** 태도다. 서버 함수(isomorphic server functions)를 쓰되, 기본 사고방식은 SPA에 가깝다. RSC 지원은 개발 중이다.

Next.js의 서버 중심 복잡도에 피로를 느낀 쪽에서 관심이 크다. State of React 2025에서도 "Next.js의 클라이언트 우선 대안"으로 자주 언급됐다.

### Qwik — 하이드레이션을 없앤다

앞에서 설명한 리주머빌리티가 이 프레임워크의 전부다. 1.x가 프로덕션 라인이고 2.0이 베타다.

접근이 급진적인 만큼 생태계는 작다. 다만 "하이드레이션이 정말 필요한가"라는 질문을 던졌다는 점에서 다른 프레임워크에도 영향을 줬다.

### SolidStart — Vite 8 위에서 다시 태어났다

**SolidStart 2가 2026년 8월에 정식 출시됐다.** 1년 넘게 25번의 알파/베타/RC를 거쳤다.

주목할 점은 **Vite 8의 Environment API 위에 직접 올라탔다**는 것이다(예전에는 Vinxi라는 추상화 계층을 거쳤다). 1편에서 말한 Environment API를 메타 프레임워크들이 기다린 이유가 이것이다. SSR·워커·엣지 같은 여러 실행 환경을 프레임워크마다 따로 만들지 않고 Vite에 맡길 수 있게 된다.

Solid 자체는 **JSX를 쓰되 가상 DOM이 없고 세밀한 반응성(fine-grained reactivity)으로 동작한다.** React 문법에 Svelte에 가까운 성능이라고 보면 대체로 맞는다.

### Angular — 조용히 많이 바뀌었다

**v22**가 2026년 6월에 나왔다.

- **zoneless가 기본**이다(v21부터). Zone.js 없이 signals로 변경 감지를 한다. v22에서는 OnPush가 기본 전략이 됐다
- **Signal Forms**와 `resource`/`httpResource`가 정식 기능이 됐다
- 빌드는 **esbuild 기반**이고, 테스트 러너 기본값이 Karma/Jasmine에서 **Vitest**로 바뀌었다. webpack 지원은 deprecated

"Angular는 무겁고 옛날 것"이라는 인상이 있다면 최근 몇 년을 안 본 것이다. 대규모 조직에서 DI·테스트·구조가 강제되는 게 장점인 상황이 분명히 있다.

### Vue — Vapor Mode는 아직 RC

Vue는 3.5.x가 안정 버전이고, **Vapor Mode가 들어가는 3.6은 아직 RC**다.

Vapor Mode는 컴파일된 컴포넌트에서 가상 DOM을 걷어내는 것이다. 방향이 Svelte와 같다. 다만 생태계(Nuxt, Vue Router, Pinia)가 따라와야 실제로 쓸 수 있다.

### 그 밖에

- **RedwoodSDK** — Cloudflare Workers 전용 React 프레임워크. RSC 우선이고 D1/R2/Durable Objects를 그대로 쓴다
- **Waku** — RSC를 최소한으로 체험해보기 위한 가벼운 React 프레임워크

**빌드 도구 칸을 보면 1편이 왜 필요했는지가 보인다.** Turbopack을 쓰는 Next.js를 빼면 전부 Vite다.

## 무엇을 고를 것인가

| 만들려는 것 | 선택 |
| --- | --- |
| 블로그, 문서, 랜딩 페이지 | **Astro** — JS를 거의 안 보낸다 |
| SEO가 중요한 서비스 (커머스, 미디어) | **Next.js** / Nuxt — ISR·PPR이 여기서 값을 한다 |
| 로그인 뒤 대시보드, 사내 관리 도구 | **Vite + React Router**(SPA) 또는 TanStack Start. SEO가 필요 없으면 SSR도 필요 없다 |
| Vue를 쓴다 | **Nuxt** |
| 번들 크기가 최우선 | **SvelteKit** |
| 큰 조직, 긴 수명, 강한 규약 | **Angular** |
| 정적 호스팅(GitHub Pages 등)만 가능 | SSG 또는 그냥 SPA |

한 가지만 덧붙이면, **SSR은 공짜가 아니다.** 서버가 늘고, 캐싱 전략을 설계해야 하고, "이 코드가 서버에서 도는가 브라우저에서 도는가"를 늘 신경 써야 하고, 배포가 복잡해진다. **SEO도 필요 없고 첫 화면이 0.5초 늦어도 되는 사내 도구라면 SPA가 더 나은 선택이다.** 도구의 유행과 내 요구사항은 다른 문제다.

## 2026년의 분위기

State of JS 2025와 State of React 2025의 결과가 흥미롭다.

- **Next.js는 사용률 1위지만 만족도에서는 밀린다.** 만족도 1위는 Astro였다
- 가장 많이 나온 불만이 **"과도한 복잡도"**였다
- 그런데 **실제 프로덕션에서는 여전히 SPA가 SSR 앱보다 많다**

정리하면 이렇다. **프레임워크 쪽의 혁신은 서버 방향으로 몰려 있지만, 현장은 그만큼 옮겨가지 않았다.** 그리고 그 간극에서 두 가지 반작용이 나왔다. 하나는 "JS를 최소한만 보내자"는 Astro 계열, 다른 하나는 "그냥 SPA로 두되 타입과 데이터만 잘 챙기자"는 TanStack Start 계열이다.

유행을 따라가는 것보다 **내가 만드는 게 어느 칸에 속하는지**를 정하는 게 먼저다.

## 이 블로그는 왜 그냥 Vite + React인가

마지막으로 자기 사례를 하나 붙인다. 이 블로그는 메타 프레임워크를 안 쓴다. Vite + React + React Router, 순수 SPA다. 마크다운을 클라이언트에서 파싱해서 그린다. 이유가 셋이다.

- **GitHub Pages에 올린다.** 정적 호스팅이라 SSR을 돌릴 서버가 없다
- **개인 블로그라 SEO 요구가 낮다.** 검색 유입으로 먹고사는 사이트가 아니다
- **다른 데모 앱(nearby, 딥페이크 탐지)이 한 저장소에 같이 있다.** 라우팅 구조가 프레임워크 규칙에 잘 안 맞는다

솔직히 말하면 **글만 놓고 보면 Astro가 정답에 가깝다.** 마크다운을 빌드 시점에 HTML로 바꿔서 JS 없이 내보내면 지금보다 훨씬 빠르고 SEO도 좋아진다. 지금 구조에서는 글 하나 읽자고 React와 마크다운 파서를 전부 받아야 한다.

그런데도 안 옮긴 이유는, 이 저장소가 블로그이면서 동시에 **React 앱 여러 개를 얹은 포트폴리오**이기 때문이다. 요구사항이 두 개면 최적해도 두 개다. 이런 판단을 하려면 결국 앞의 표들이 머릿속에 있어야 한다.

## 정리

- SPA의 대가(첫 화면, 번들 크기, SEO, 데이터 폭포)를 해결하려고 프레임워크가 서버로 갔다
- 축은 둘이다 — **HTML을 언제 만드는가**, **만든 뒤 JS로 무엇을 하는가**
- **하이드레이션**은 서버가 만든 HTML에 이벤트를 붙이는 과정이고, 같은 일을 두 번 하며 "보이는데 안 눌리는" 구간을 만든다
- 아일랜드는 하이드레이션 범위를 줄이고, 리주머빌리티는 없애고, RSC는 클라이언트로 갈 코드를 줄인다
- **RSC ≠ SSR.** SSR은 첫 화면을 빨리 주는 것, RSC는 번들에서 코드를 빼는 것이다
- Next.js는 기능이 가장 많고 복잡도도 가장 높다. Cache Components로 캐싱이 명시적 opt-in으로 바뀌었다
- 콘텐츠 사이트는 Astro, Vue는 Nuxt, 번들 크기는 SvelteKit, 큰 조직은 Angular
- **Turbopack을 쓰는 Next.js를 빼면 거의 전부 Vite 위에 있다**
- SSR은 공짜가 아니다. SEO가 필요 없는 사내 도구라면 SPA가 더 낫다
- 2026년 현재 혁신은 서버 쪽에 몰려 있지만 현장은 여전히 SPA가 많다
