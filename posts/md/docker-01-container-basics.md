## 이 시리즈에 대해

도커는 명령어 대여섯 개만 외우면 당장 뭔가는 돌아간다. 문제는 그다음이다. 빌드가 느려지고, 컨테이너를 지웠더니 DB 데이터가 날아가고, 컨테이너끼리 `localhost`로 통신이 안 되고, 이미지가 1.2GB가 된다. 전부 **컨테이너가 실제로 무엇인지를 모르고 명령어만 외웠을 때** 생기는 일이다.

그래서 밑에서부터 다시 정리한다. 목표는 "개발자가 자기 애플리케이션을 컨테이너로 만들어서 안전하게 굴릴 수 있는 수준"이다. 쿠버네티스 같은 오케스트레이션은 [8편](/post/docker-08-optimize-operate)에서 경계만 그어둔다.

## 왜 도커를 쓰는가

"내 노트북에서는 됐는데요"라는 말의 정체는 대부분 이 셋 중 하나다.

- **런타임 버전이 다르다** — 로컬은 Node 20, 서버는 Node 16
- **시스템 라이브러리가 다르다** — 로컬 Ubuntu에는 있고 서버 CentOS에는 없는 `.so`
- **설정이 코드 밖에 있다** — 누군가 서버에서 손으로 고쳐둔 환경변수, 심볼릭 링크, 커널 파라미터

도커는 이걸 "애플리케이션 + 그것이 필요로 하는 파일시스템 전체"를 한 덩어리(이미지)로 묶어서 해결한다. 실행 환경을 서버가 아니라 **이미지가 들고 다닌다.** 서버에 남는 요구사항은 "컨테이너 런타임이 깔려 있을 것" 하나로 줄어든다.

부수 효과가 더 크다.

- 환경 구성이 `Dockerfile`이라는 **텍스트 파일로 버전 관리**된다. 위키에 적힌 설치 절차와 달리 실행해서 검증할 수 있다.
- 같은 서버에서 서로 다른 버전의 MySQL을 동시에 띄울 수 있다.
- 개발 환경 세팅이 `docker compose up` 한 줄이 된다.
- 서버를 "고쳐 쓰는 것"이 아니라 **버리고 새로 만드는 것**으로 다루게 된다(불변 인프라).

## 가상머신과 컨테이너

가장 흔한 오해가 "컨테이너는 가벼운 가상머신"이다. 결과가 비슷해 보일 뿐 원리가 다르다.

```
[ 가상머신 ]                        [ 컨테이너 ]

 앱 A     앱 B                       앱 A     앱 B
 라이브러리                           라이브러리
 게스트 OS 커널  ← 각자 커널 O        (게스트 커널 없음)
 하이퍼바이저                         컨테이너 런타임
 호스트 OS 커널                       호스트 OS 커널  ← 공유
 하드웨어                             하드웨어
```

핵심은 **커널을 공유하느냐**다.

| | 가상머신 | 컨테이너 |
| --- | --- | --- |
| 격리 단위 | 가상 하드웨어 | 프로세스 |
| 커널 | 게스트마다 별도 | 호스트 커널 공유 |
| 부팅 시간 | 수십 초 | 수십 밀리초 |
| 이미지 크기 | GB 단위 | MB 단위 |
| 격리 강도 | 강함 (하드웨어 경계) | 상대적으로 약함 (커널 경계) |
| 다른 OS 실행 | 가능 (리눅스 위에 윈도우) | 불가 (커널이 같아야 함) |

여기서 두 가지 실무 결론이 나온다.

1. **컨테이너는 커널을 공유하므로, 리눅스 컨테이너는 리눅스 커널 위에서만 돈다.** 맥이나 윈도우에서 도커가 도는 건 뒤에서 리눅스 VM을 하나 띄워두기 때문이다. 그래서 맥에서 바인드 마운트 I/O가 느린 것도 이 구조 때문이다.
2. **격리가 VM만큼 강하지 않다.** 커널 취약점 하나로 호스트까지 뚫릴 수 있다. 신뢰할 수 없는 코드를 남의 컨테이너와 같은 커널에서 돌리는 건 위험하다. 8편의 보안 이야기가 전부 여기서 출발한다.

## 컨테이너를 만드는 리눅스 커널 기능

컨테이너는 도커가 발명한 게 아니다. 리눅스 커널에 이미 있던 기능들을 조합해서 "격리된 프로세스"를 만든 것이고, 도커는 그걸 쓰기 편하게 포장했다.

### 1. 네임스페이스 (namespace) — 무엇이 보이는가

프로세스가 볼 수 있는 시스템 자원의 범위를 잘라낸다. "격리"의 실체다.

| 네임스페이스 | 격리 대상 |
| --- | --- |
| `pid` | 프로세스 ID — 컨테이너 안의 첫 프로세스가 PID 1이 된다 |
| `net` | 네트워크 인터페이스, IP, 포트, 라우팅 테이블 |
| `mnt` | 마운트 포인트 — 자기만의 파일시스템 트리 |
| `uts` | 호스트명, 도메인명 |
| `ipc` | 공유 메모리, 세마포어 |
| `user` | UID/GID 매핑 — 컨테이너의 root를 호스트의 일반 유저로 매핑 |
| `cgroup` | cgroup 계층 뷰 |

컨테이너 안에서 `ps`를 쳤을 때 호스트의 프로세스가 안 보이는 이유가 pid 네임스페이스다. `ifconfig`에 호스트 랜카드가 안 보이는 건 net 네임스페이스다.

### 2. cgroup — 얼마나 쓸 수 있는가

네임스페이스가 "시야"를 자른다면 cgroup은 **자원 사용량**을 자른다. CPU, 메모리, 디스크 I/O, 네트워크 대역폭을 그룹 단위로 제한하고 계측한다.

`docker run --memory=512m --cpus=1.5`가 그대로 cgroup 설정으로 내려간다. [3편](/post/docker-03-run-lifecycle)에서 자세히 본다.

메모리 한도를 넘기면 컨테이너 안의 프로세스가 커널 OOM Killer에 죽는다. 컨테이너가 종료 코드 137로 죽어 있으면 십중팔구 이것이다(128 + SIGKILL 9).

### 3. 유니온 파일시스템 (OverlayFS) — 파일이 어떻게 쌓이는가

여러 디렉터리를 겹쳐서 하나처럼 보여준다. 이미지 레이어의 근간이고, [2편](/post/docker-02-image-registry)의 주제다.

```
       ┌──────────────────────────┐
       │ 컨테이너 레이어 (쓰기 가능) │  ← 컨테이너마다 하나씩
       ├──────────────────────────┤
       │ 이미지 레이어 3 (읽기 전용) │  ┐
       │ 이미지 레이어 2 (읽기 전용) │  │ 여러 컨테이너가 공유
       │ 이미지 레이어 1 (읽기 전용) │  ┘
       └──────────────────────────┘
                  ↓
          하나의 파일시스템으로 보임
```

아래 레이어의 파일을 수정하면 원본을 건드리지 않고 위 레이어로 복사해서 고친다(Copy-on-Write). **컨테이너를 지우면 맨 위 레이어가 사라지므로 그 안의 변경도 같이 사라진다.** DB 컨테이너를 지웠더니 데이터가 날아갔다는 이야기의 정체가 이것이고, [5편](/post/docker-05-volume-data)의 볼륨이 그 해법이다.

### 4. 그 밖에

- **capabilities** — root 권한을 잘게 쪼갠 것. 컨테이너의 root는 호스트 root보다 훨씬 적은 권한만 갖는다.
- **seccomp** — 허용할 시스템 콜 목록. 도커는 기본 프로파일로 위험한 콜을 막는다.
- **AppArmor / SELinux** — 강제 접근 제어.

`--privileged` 옵션은 이 안전장치를 **전부 끈다.** 편해 보인다고 습관적으로 쓰면 컨테이너 탈출 경로를 열어주는 것과 같다.

## 컨테이너는 그냥 프로세스다

이 문장이 이번 편에서 가장 중요하다. 직접 확인해보자.

```bash
docker run -d --name demo nginx:alpine
```

호스트에서 프로세스를 찾아보면 그대로 보인다.

```bash
ps -ef | grep nginx
# root  12345  12300  0 10:00 ?  00:00:00 nginx: master process nginx -g daemon off;
```

반면 컨테이너 안에서 보면 자기 자신뿐이다.

```bash
docker exec demo ps -ef
# PID   USER     COMMAND
#   1   root     nginx: master process nginx -g daemon off;
#  30   nginx    nginx: worker process
```

같은 프로세스인데 **호스트에서는 12345번, 컨테이너 안에서는 1번**이다. pid 네임스페이스가 번호를 다시 매긴 것이다. 호스트명도 마찬가지다.

```bash
hostname                 # my-laptop
docker exec demo hostname  # 3f2a1b9c4d5e  ← 컨테이너 ID
```

여기서 따라오는 결론들이 있다.

- **컨테이너에는 "부팅"이 없다.** 프로세스 하나를 실행할 뿐이다. 그래서 시작이 빠르다.
- **그 프로세스가 끝나면 컨테이너도 끝난다.** `docker run ubuntu`가 곧바로 종료되는 이유다. 실행할 게 `bash`인데 입력이 붙어 있지 않으니 바로 끝난다.
- **컨테이너 안의 PID 1은 특별한 책임을 진다.** 시그널 처리와 좀비 프로세스 수거가 그것인데, 대부분의 앱은 그걸 안 하도록 만들어져 있다. 3편의 `--init`과 4편의 `ENTRYPOINT` 이야기가 여기서 나온다.

## 도커의 실행 구조

`docker run`을 쳤을 때 실제로 움직이는 것들이다.

```
 docker CLI ──(REST API / Unix 소켓)──▶ dockerd (도커 데몬)
                                          │
                                          ▼
                                      containerd        ← 컨테이너 수명 관리
                                          │
                                          ▼
                                    containerd-shim
                                          │
                                          ▼
                                        runc            ← 실제로 네임스페이스/cgroup 설정
                                          │
                                          ▼
                                     내 프로세스
```

- **docker CLI** — 우리가 치는 명령어. 그냥 HTTP 클라이언트다. 기본적으로 `/var/run/docker.sock` 유닉스 소켓으로 데몬에 요청한다.
- **dockerd** — 이미지 빌드, 네트워크·볼륨 관리, API 제공. 실제 실행은 아래로 넘긴다.
- **containerd** — 이미지 가져오기와 컨테이너 수명 관리를 맡는 런타임. 지금은 CNCF 프로젝트로 독립해 있고, 쿠버네티스도 이걸 직접 쓴다.
- **runc** — OCI 런타임 스펙 구현체. 네임스페이스를 만들고 cgroup을 걸고 프로세스를 띄우는, 진짜 일을 하는 부분.
- **shim** — 데몬이 재시작돼도 컨테이너가 살아 있게 중간에서 붙잡아주는 프로세스.

두 가지를 기억할 만하다.

1. **`docker.sock`에 접근할 수 있다는 건 사실상 호스트 root 권한이다.** 그 소켓으로 `--privileged` 컨테이너를 만들 수 있기 때문이다. 사용자를 `docker` 그룹에 넣는 것, 컨테이너에 소켓을 마운트하는 것 모두 이 의미를 갖는다.
2. **OCI 표준(이미지 스펙 + 런타임 스펙)이 있어서 도커가 유일한 선택지가 아니다.** Podman, containerd + nerdctl, CRI-O가 같은 이미지를 실행한다. 쿠버네티스는 1.24에서 도커 런타임 지원을 걷어냈지만, 도커로 만든 이미지는 그대로 쓴다. **"도커 이미지"가 아니라 OCI 이미지**라고 생각하는 편이 정확하다.

### 맥과 윈도우에서는

리눅스 커널이 없으므로 도커가 경량 리눅스 VM을 하나 띄우고 그 안에서 컨테이너를 돌린다. Docker Desktop이 그 VM과 파일 공유, 포트 포워딩을 대신 처리해준다.

- 윈도우에서는 WSL2 백엔드를 쓰는 게 성능상 유리하다. 소스 코드도 `/mnt/c/...`가 아니라 **WSL2 파일시스템 안(`~/projects/...`)에 두는 것**이 빠르다. 파일시스템 경계를 넘을 때마다 비용이 붙는다.
- 맥에서는 바인드 마운트가 느린 것이 구조적이다. `:cached`, `:delegated` 옵션이나 VirtioFS 설정으로 완화한다.
- Docker Desktop은 일정 규모 이상의 기업에서는 유료다. 대안으로 Colima, Rancher Desktop, Podman Desktop이 있다.

## 설치 확인과 첫 컨테이너

```bash
docker version   # 클라이언트와 서버(데몬) 버전을 각각 보여준다
docker info      # 스토리지 드라이버, 컨테이너 수, 루트 디렉터리 등
```

`docker version`에서 Server 쪽이 안 나오면 데몬이 안 떠 있거나 권한이 없는 것이다. 리눅스에서 `permission denied`가 뜨면 `sudo usermod -aG docker $USER` 후 재로그인한다(위에서 말한 보안 의미를 이해한 상태에서).

### hello-world 분해하기

```bash
docker run hello-world
```

이 한 줄에서 벌어지는 일은 이렇다.

1. 로컬에 `hello-world:latest` 이미지가 있는지 본다 → 없다
2. Docker Hub에서 이미지를 **pull** 한다
3. 이미지로 컨테이너를 **만든다**(create) — 맨 위에 쓰기 가능 레이어를 얹는다
4. 컨테이너를 **시작한다**(start) — 네임스페이스·cgroup을 설정하고 지정된 프로세스를 실행한다
5. 프로세스가 메시지를 출력하고 종료 → 컨테이너도 종료(Exited)

`docker run`은 `pull` + `create` + `start`를 합친 편의 명령이다. 이 분해가 3편의 생명주기 이야기의 출발점이다.

### nginx 띄워보기

```bash
docker run -d -p 8080:80 --name web nginx:alpine
```

브라우저에서 `http://localhost:8080`을 열면 nginx 기본 페이지가 뜬다. 옵션의 의미는 이렇다.

- `-d` (detach) — 백그라운드로 실행하고 컨테이너 ID를 출력한다
- `-p 8080:80` — **호스트의 8080을 컨테이너의 80으로** 연결한다. 순서는 항상 `호스트:컨테이너`
- `--name web` — 이름을 붙인다. 안 붙이면 `hungry_einstein` 같은 이름이 자동 생성된다
- `nginx:alpine` — `이미지이름:태그`

상태를 확인하고 정리한다.

```bash
docker ps                # 실행 중인 컨테이너
docker ps -a             # 종료된 것까지 전부
docker logs -f web       # 로그 실시간 확인
docker exec -it web sh   # 컨테이너 안에서 셸 열기
docker stop web          # SIGTERM 후 10초 뒤 SIGKILL
docker rm web            # 컨테이너 삭제 (중지 상태여야 함)
```

`-p`를 빼먹으면 컨테이너는 잘 돌지만 밖에서 접근할 수 없다. 컨테이너가 자기만의 네트워크 네임스페이스를 갖기 때문인데, [6편](/post/docker-06-network)에서 그 구조를 본다.

## 명령어 지도

지금 전부 외울 필요는 없다. 어떤 대상에 어떤 동사가 붙는지의 **구조**만 잡아두면 된다.

| 대상 | 자주 쓰는 명령 |
| --- | --- |
| 이미지 | `pull` `push` `build` `images` `tag` `rmi` `history` `inspect` `save` `load` |
| 컨테이너 | `run` `create` `start` `stop` `restart` `kill` `rm` `ps` `logs` `exec` `cp` `stats` `top` `inspect` |
| 볼륨 | `volume create` `ls` `inspect` `rm` `prune` |
| 네트워크 | `network create` `ls` `inspect` `connect` `disconnect` `rm` |
| 시스템 | `info` `version` `system df` `system prune` `events` |
| Compose | `compose up` `down` `logs` `ps` `exec` `build` `pull` |

최신 도커는 `docker image ls`, `docker container ls`처럼 **대상을 명시하는 형태**를 정식으로 삼는다. `docker images`, `docker ps`는 짧은 별칭이다.

디스크가 부족해지면 이 두 줄을 기억해두면 된다.

```bash
docker system df           # 이미지/컨테이너/볼륨/캐시가 각각 얼마나 쓰는지
docker system prune -a     # 안 쓰는 것 전부 삭제 (볼륨은 --volumes를 붙여야 포함)
```

`prune -a`는 **실행 중이 아닌 컨테이너가 참조하지 않는 모든 이미지**를 지운다. 다시 받으면 그만인 개발 머신에서는 편하지만, 운영 서버에서는 롤백용 이전 버전 이미지까지 날아갈 수 있으니 주의한다.

## 격리를 직접 확인해보기

읽는 것보다 한 번 깨보는 게 낫다.

```bash
# 1) 파일시스템이 분리되어 있다
docker run --rm alpine ls /
# bin dev etc home lib ... ← 호스트가 아니라 alpine 이미지의 루트

# 2) 프로세스가 분리되어 있다
docker run --rm alpine ps -ef
# PID 1이 ps 자기 자신뿐이다

# 3) 네트워크가 분리되어 있다
docker run --rm alpine ip addr
# lo와 eth0(172.17.x.x)만 있다. 호스트 랜카드는 없다

# 4) 그런데 커널은 공유한다
uname -r                          # 5.15.x (호스트)
docker run --rm alpine uname -r   # 5.15.x ← 똑같다!
```

마지막 줄이 핵심이다. Alpine 이미지 안에는 커널이 들어 있지 않다. 우리가 "이미지"라고 부르는 건 **커널을 뺀 나머지 파일시스템**이다.

호스트 네임스페이스를 빌려 쓰면 격리가 어떻게 풀리는지도 볼 수 있다.

```bash
docker run --rm --pid=host alpine ps -ef | head
# 호스트의 모든 프로세스가 보인다
```

## 자주 하는 오해

- **"컨테이너는 가벼운 VM이다"** — 커널을 공유하는 격리된 프로세스다. OS가 통째로 들어 있지 않다.
- **"컨테이너 안은 안전하다"** — 커널을 공유하므로 VM 수준의 경계가 아니다. `--privileged`, `docker.sock` 마운트, root 실행은 전부 그 경계를 더 얇게 만든다.
- **"이미지와 컨테이너는 같은 말이다"** — 이미지는 클래스, 컨테이너는 인스턴스다. 이미지 하나로 컨테이너 100개를 만들 수 있다.
- **"컨테이너에 SSH를 넣어야 접속할 수 있다"** — `docker exec`가 있다. 컨테이너에 sshd를 넣는 건 프로세스 하나 원칙을 깨는 안티패턴이다.
- **"컨테이너를 재시작하면 데이터가 사라진다"** — 재시작(`restart`)은 살아남는다. 사라지는 건 컨테이너를 **삭제**(`rm`)했을 때다. 그래도 데이터를 붙잡아두려면 볼륨을 쓴다.
- **"도커가 없어졌으니 도커를 배울 필요 없다"** — 쿠버네티스가 런타임으로 도커를 안 쓸 뿐, 이미지 포맷과 개념은 그대로다. 로컬 개발에서는 여전히 도커가 표준이다.

## 정리

이번 편에서 잡아야 할 것.

- 컨테이너는 커널을 공유하는 **격리된 프로세스**다. VM이 아니다
- 격리는 네임스페이스(시야) + cgroup(자원) + 유니온 파일시스템(디스크)의 조합이다
- 이미지에는 커널이 없다. 그래서 리눅스 컨테이너는 리눅스 커널 위에서만 돈다
- 컨테이너의 쓰기 레이어는 컨테이너를 지우면 사라진다 → 5편 볼륨
- `docker CLI → dockerd → containerd → runc` 순으로 내려간다. OCI 표준 덕에 런타임은 갈아끼울 수 있다
- `docker.sock` 접근 권한은 사실상 호스트 root 권한이다
- `docker run` = `pull` + `create` + `start`
- 포트 매핑은 `-p 호스트:컨테이너` 순서다
- PID 1이 종료되면 컨테이너도 종료된다

다음 편에서는 이미지가 레이어로 어떻게 쌓이는지, 태그와 레지스트리를 어떻게 다루는지 정리한다.
