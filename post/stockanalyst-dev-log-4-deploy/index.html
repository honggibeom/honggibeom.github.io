StockAnalyst 개발기 (4) - 클라우드 견적을 내다 집에 서버를 올린 기록

2026.09.05 · #stockanalyst #배포 #docker #cloudflare #oauth2 #mysql

StockAnalyst 는 Spring Boot + React(Vite) + Python 파이프라인으로 만든 주식 정보 서비스다. 전체 구조는 개발기 (2) 목차에 있다. 2편은 "운영 배포는 아직이다"로 끝났고, 이 글은 그 배포 전 목록을 들고 실제로 서버를 올린 기록이다.

한눈에 보기

  • OCI 무료 A1 은 며칠을 재시도해도 용량 부족으로 안 잡혔다. 서울·춘천은 가용 도메인이 하나뿐이라 우회로도 없다
  • 유료까지 전부 견적을 냈고 결국 집 PC 로 갔다. 결정적인 이유는 가격이 아니라 데이터가 이미 거기 있다는 것
  • mem_limit 을 눈대중으로 잡아 뒀던 걸 다시 계산했다. ONNX 가중치가 힙 밖이라 헤드룸이 필요하다
  • Cloudflare Tunnel 로 공유기에 포트를 하나도 열지 않고 공개했다
  • TLS 를 엣지에서 끊으면 오리진은 평문 HTTP 라 구글 OAuth 가 통째로 깨진다
  • 이번 작업에서 어려웠던 건 도커도 터널도 아니고 같은 이름이 두 곳을 가리키는 상황이었다

2편이 남긴 배포 전 필수 목록은 셋이었다. ddl-auto 를 validate 로 바꾸기, secret 파일 대신 환경변수 주입으로 전환하기, 노출 이력 있는 키 로테이션하기. 그 목록을 들고 시작했다.

결론부터 쓰면 클라우드를 접고 집 PC 에 올렸다. 그 결정에 이르기까지 견적을 꽤 봤고, 올리는 과정에서 예상 못 한 데서 여러 번 넘어졌다. 순서는 실제로 부딪힌 순서다.

1. 어디에 올릴 것인가

원래 계획은 OCI Always Free였다. Ampere A1 을 공짜로 주니 당연히 그쪽이라고 생각했다. 그런데 생성 버튼을 누를 때마다 이 메시지가 나왔다.

가용성 도메인 VM.Standard.A1.Flex에서 AD-1 셰이프에 대한 용량이 부족합니다.

오류 메시지는 "다른 가용성 도메인을 시도하라"고 안내하는데, 서울·춘천 리전은 가용 도메인이 하나뿐이라 시도할 다른 곳이 없다. 며칠을 재시도해도 안 잡혔다.

그래서 유료를 포함해 전부 견적을 냈다.

몇 가지 배운 게 있다.

EC2 로 인스턴스 타입을 고르는 순간 이 규모에서는 무조건 비싼 길로 들어간다. 같은 AWS 라도 Lightsail 8GB(59,800원)가 EC2 t4g.large(82,000원 + EBS + 트래픽)보다 싸고 스토리지와 트래픽이 정액으로 포함된다. 오토스케일링이나 세밀한 인스턴스 튜닝이 필요 없으면 EC2 를 쓸 이유가 없다.

t2 계열은 지금 고를 이유가 전혀 없다. t2.xlarge(시간당 0.2304달러)는 같은 4 vCPU / 16GiB 인 t4g.xlarge(0.1664달러)보다 38% 비싸고 네트워크 등급도 낮다. Nitro 이전 세대다. 게다가 t2 는 CPU 크레딧을 다 쓰면 기준 성능으로 떨어지는데, 초과분을 돈으로 메우는 Unlimited 모드가 기본으로 꺼져 있다. 이 서비스는 예측 버튼 한 번에 2,600개 시퀀스를 ONNX 모델 3개에 밀어넣고 몬테카를로는 5만 경로를 돌린다. CPU 가 짧고 굵게 튀는 패턴이라 t2 에서는 크레딧이 빨리 마른다.

OCI 유료 셰이프는 OCPU 정의를 봐야 한다. x86(E4·E5·Standard3)은 1 OCPU 가 물리 코어 1개에 하이퍼스레딩까지 해서 2 vCPU 고, Ampere A1 은 1 OCPU 가 1 vCPU 다. 같은 "2코어 12GB"라도 AMD 는 스레드가 4개, ARM 은 2개다. 단가는 A1 이 OCPU 시간당 0.01달러, E4 가 0.025달러로 2.5배 차이 난다. 메모리는 셰이프와 무관하게 GB 시간당 0.0015달러로 같아서 차이는 전부 CPU 에서 난다.

AWS 프리티어는 2025년 7월부터 성격이 바뀌었다. 신규 계정은 가입 시 100달러 크레딧에 활동으로 최대 100달러를 더해 200달러를 받고, 6개월 또는 크레딧 소진 중 먼저 오는 시점에 끝난다. 예전의 12개월 t2.micro 750시간은 신규 계정에 안 나온다. Lightsail 4GB 로 쓰면 6개월 만료가 먼저 오고, 그 뒤엔 월 32,600원이 그대로 청구된다. 체험권이지 운영 기반이 아니다.

그래서 로컬

견적을 다 보고 나니 로컬이 남았다. 결정적인 이유는 가격이 아니라 데이터가 이미 거기 있다는 것이었다.

DB 가 1.69GB, models/ 가 327MB, krx 파이프라인이 전부 이 PC 에서 돈다. 클라우드로 가면 수집은 개발 PC 에서 하고 서비스는 클라우드에서 하니 DB 가 두 벌이 되고, 배포할 때마다 덤프와 이관이 붙는다. 로컬이면 그 문제가 통째로 사라진다. 사양도 32GB 에 RTX 3070 Ti 라 A1 12GB 보다 낫고, 감성 모델 재학습을 같은 기계에서 할 수 있다.

다만 공짜는 아니다. 정직하게 적어 둔다.

항목내용
전기요금유휴에서도 6090W 는 나가고 24시간이면 월 4070kWh. 누진 구간에 따라 월 1~2만원. Contabo 일본 8GB 가 7,000원대인 걸 감안하면 순수 비용만으로는 로컬이 더 비쌀 수도 있다
백업클라우드는 볼륨 스냅샷 한 줄이면 되는데 집은 직접 만들어야 한다. 디스크가 죽으면 10년치 캔들과 뉴스 감성 라벨이 같이 날아간다

로컬의 값어치는 돈이 아니라 데이터 단일화와 사양에 있다. 백업이 유일한 구조적 약점이다.

2. 필요 메모리를 실제로 계산했다

compose 의 mem_limit 을 눈대중으로 잡아 뒀었다. backend 5g, mysql 4g 에 버퍼풀 3G. 근거를 물어보니 없었다. 다시 계산했다.

먼저 mem_limit 은 예약이 아니라 cgroup 상한이다. 도커가 그만큼 잡아두는 게 아니라 "이 선을 넘으면 죽인다"는 뜻이다. 그래서 상한을 넉넉히 잡는 것 자체는 비용이 아니다.

다만 백엔드는 이 값이 실제 동작에 영향을 준다. Dockerfile 의 -XX:MaxRAMPercentage=70 이 컨테이너 한도를 읽어 힙 상한을 정하기 때문이다. mem_limit 4g 의 70%면 힙 상한이 2.8GB 고, 남는 1.2GB 가 힙 밖 몫이다.

여기서 중요한 건 ONNX 가중치가 힙 밖이라는 점이다. models/sentiment/model_quantized.onnx 가 338MB 인데, onnxruntime 이 로드하면 자바 힙이 아니라 네이티브 메모리에 올라가고 추론 arena 도 힙 밖이다. 여기에 signal 모델 3개의 배치 추론이 얹힌다. 힙 기준으로만 한도를 빡빡하게 잡으면 JVM 은 자기 힙이 안 찼다고 판단하는데 커널이 컨테이너를 죽인다(exit 137). 30% 헤드룸은 그 몫이다.

항목필요근거
OS + 도커 데몬0.7GB
MySQL 81.5~2GBDB 1.69GB. 버퍼풀 2G + 자체 오버헤드 0.5GB 안팎
백엔드 JVM2~2.5GB힙 0.31.0 + ONNX 네이티브 0.40.8 + Metaspace·코드캐시 0.25
Redis0.25GB캐시 용도
프론트 nginx0.13GB실측 20MB
합계약 4.6~5.6GB6GB 가 현실적 최소

계산해 보니 5g 로 잡아 뒀던 백엔드는 3~4g 면 충분했다.

그리고 MySQL 쪽에서 실제 위험을 하나 찾았다. 버퍼풀은 상한이 아니라 실제 할당인데, 그 위에 커넥션별 정렬·조인 버퍼, 임시 테이블, 로그 버퍼, 딕셔너리 캐시가 더 얹힌다. 통상 버퍼풀은 컨테이너 한도의 70% 이하로 잡는다. 기존 설정은 3G/4g 로 75%였다. 커넥션이 몰리거나 큰 정렬이 들어오면 컨테이너가 OOM 으로 MySQL 을 죽이는 구간이다. 로그 없이 재시작만 보이는 유형이라 원인 찾기도 성가시다.

DB 전체가 1.69GB 라 버퍼풀 2G 면 통째로 캐시된다. 더 올려도 채울 데이터가 없다. 2G/4g 로 50%까지 내렸다.

-- DB 실제 크기 확인
SELECT ROUND(SUM(data_length + index_length)/1024/1024/1024, 2) gb
FROM information_schema.tables
WHERE table_schema = 'stock_information_backend';

3. 포트를 열지 않고 공개하기

집에서 서비스하려면 외부에서 들어올 길이 필요하다. 선택지는 셋이었다.

도메인포트포워딩인증서
무료 서브도메인 + nginx + Let's Encrypt무료필요certbot
도메인 구매 + Cloudflare 프록시 모드연 1만원대필요Cloudflare 자동
도메인 구매 + Cloudflare Tunnel연 1만원대불필요Cloudflare 자동

세 번째를 골랐다. Cloudflare Tunnel 은 cloudflared 가 밖으로 나가는 연결만 쓴다. 공유기에 열린 구멍이 없으니 스캐너가 집에서 찾을 게 없다.

프록시 모드(A 레코드에 주황 구름)와 비교하면 차이가 분명하다. 프록시 모드에서도 원본 IP 는 숨겨지지만 새는 경로가 여럿 있다. 과거 DNS 이력을 보관하는 서비스, 프록시를 안 건 서브도메인 하나, 서버가 밖으로 보내는 요청의 출발지 IP. 그리고 Cloudflare 엣지 IP 대역만 허용하도록 방화벽을 잠가야 하는데 그 목록은 수시로 바뀐다. 터널은 원본 IP 가 DNS 어디에도 존재하지 않아서 샐 자리가 없다.

대가도 있다. 홉이 하나 늘고, cloudflared 가 죽으면 사이트가 통째로 내려간다. 프록시 모드는 급하면 주황 구름을 꺼서 DNS 직결로 돌릴 수 있는데 터널은 그 탈출구가 없다. 그래도 집 네트워크를 인터넷에 여느냐 마느냐의 차이라 다른 항목들과 무게가 다르다고 봤다.

무료 도메인이 안 되는 이유

처음엔 kro.kr 같은 무료 서브도메인을 쓰려 했다. 두 가지에서 막혔다.

Cloudflare 무료 플랜은 CNAME 부분 설정을 지원하지 않는다. 부분 설정은 Business 이상이고, 무료는 도메인의 네임서버 자체를 Cloudflare 로 위임해야 한다. 내도메인.한국의 무료 서브도메인은 네임서버를 바꿀 수 없으니 애초에 존으로 올릴 수가 없다.

포트포워딩과 Let's Encrypt 로 가더라도 함정이 있다. Let's Encrypt 는 등록 도메인당 7일에 인증서 50장으로 제한하고, 등록 도메인 판정에 Public Suffix List 를 쓴다. 그런데 목록을 뒤져 보니 kro.kr 은 거기 없다. PSL 의 .kr 섹션에 있는 건 하이픈 없는 공식 2단계 도메인(pe.kr, or.kr, ne.kr)이고, 내도메인.한국이 나눠주는 하이픈 버전은 별개 문자열이다. 즉 kro.kr 을 쓰는 전 세계 사용자가 주당 50장 버킷 하나를 나눠 쓴다. 갱신도 이 카운트에 들어간다. "특정 시각에 예약 실행을 걸어 티케팅하듯 발급받았다"는 후기가 나오는 이유가 이거다.

.kr 도메인을 샀다. 연 1만원대인데, 24시간 가동 전기요금이 월 1~2만원이니 도메인 1년치가 전기요금 열흘치보다 싸다. 무료 호스트명을 찾느라 쓰는 시간이 더 비쌌다.

가비아에서 사고 네임서버만 Cloudflare 것으로 바꿨다. 소유자 인증을 거쳐야 저장되고 반영은 최대 48시간이라는데 실제로는 훨씬 빨랐다.

터널은 TUNNEL_TOKEN 방식(원격 관리형)을 썼다. Zero Trust 에서 터널을 만들면 OS 별 설치 명령이 나오는데, 컨테이너로 돌리니 그 명령은 쓰지 않고 --token 뒤의 문자열만 가져다 .env 에 넣는다.

cloudflared:
  image: cloudflare/cloudflared:latest
  command: tunnel --no-autoupdate run
  environment:
    TUNNEL_TOKEN: ${CF_TUNNEL_TOKEN}

라우팅은 대시보드에서 Public Hostname 을 http://frontend:80 으로 건다. frontend 는 compose 서비스명이고, cloudflared 가 같은 네트워크에 있어서 이름으로 찾아간다. 직접 docker run 으로 띄우면 compose 네트워크 밖이라 이 이름을 못 찾는다.

4. TLS 를 엣지에서 끊으면 OAuth 가 깨진다

터널을 붙이고 나서 만난 함정이다. 로그인을 테스트하기 전에 발견해서 다행이었다.

Cloudflare 가 TLS 를 엣지에서 종단하고 오리진에는 평문 HTTP 로 넘긴다. 그래서 컨테이너 안 nginx 에서 $scheme 은 항상 http 다. 기존 설정은 그 값을 그대로 넘기고 있었다.

proxy_set_header X-Forwarded-Proto $scheme;

이러면 백엔드가 자기 주소를 http:// 로 인식한다. Spring Security OAuth2 의 redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}" 에서 {baseUrl} 이 http:// 로 만들어지고, 구글은 HTTPS 가 아닌 리디렉션 URI 를 거부한다. localhost 만 예외다. 로그인이 통째로 죽는다.

cloudflared 는 원래 스킴을 X-Forwarded-Proto: https 로 붙여서 보낸다. 그 값을 살리고 없을 때만 $scheme 으로 떨어지게 map 을 뒀다.

map $http_x_forwarded_proto $forwarded_proto {
    default $http_x_forwarded_proto;
    ""      $scheme;
}
...
proxy_set_header X-Forwarded-Proto $forwarded_proto;
proxy_set_header X-Forwarded-Host  $host;

백엔드도 그 헤더를 읽게 해야 한다.

server:
  forward-headers-strategy: FRAMEWORK

백엔드 포트는 외부에 열지 않고 nginx 만 접근하므로 헤더를 신뢰해도 된다. NATIVE(Tomcat RemoteIpValve)도 되지만 신뢰 프록시 대역 설정이 따라와서 FRAMEWORK 가 단순하다.

구글 쪽에서도 세 군데를 손봐야 한다. 2025년 개편으로 "OAuth 동의 화면"이 Google Auth Platform 으로 바뀌면서 위치가 달라졌다.

메뉴할 일
Branding승인된 도메인에 도메인 추가 (https:// 없이)
Clients승인된 리디렉션 URI 에 https://도메인/login/oauth2/code/google
Audience테스트에서 게시(In production)로

세 번째를 빠뜨리면 콘솔에 일일이 등록한 최대 100명만 로그인된다. 다행히 이 앱은 scope: profile, email 만 써서 비민감 스코프라 검증 절차 없이 게시할 수 있다. 다만 동의 화면에 앱 이름과 로고를 표시하려면 별도의 브랜드 검증이 필요하다. 로고는 나중에 하기로 하고 먼저 게시했다.

5. 기밀 설정을 이미지에서 빼기

2편의 숙제 중 하나였다. 보안과 설정 글에서 만든 application-secret.yml 이 jar 에 구워져서 이미지를 어디에도 올릴 수 없는 상태였다.

해법은 세 줄이다.

// build.gradle
bootJar {
    archiveFileName = 'app.jar'
    exclude '**/application-secret.yml'
}

# application.yml
spring:
  config:
    import: optional:classpath:application-secret.yml

bootJar 에서만 제외하니 IDE 로컬 실행은 build/resources/main 을 읽어서 영향이 없다. 컨테이너에는 파일이 없으므로 optional 이어야 기동한다.

주입은 Spring 의 환경변수 relaxed binding 에 맡겼다. 이게 이 작업에서 가장 중요한 판단이었다. JWT_SECRET 이 jwt.secret 으로, KIS_APP_KEY 가 kis.app-key 로 자동 매핑되고, 환경변수가 설정 파일보다 우선순위가 높다.

application.yml 에 jwt.secret: ${JWT_SECRET} 같은 플레이스홀더를 추가하면 오히려 망가진다. spring.config.import 로 가져온 문서는 가져오는 쪽보다 우선순위가 낮아서, application.yml 에 키를 명시하면 그게 secret 파일을 덮어쓴다. 환경변수가 없는 IDE 개발 환경에서 값이 사라진다. 아무것도 추가하지 않는 게 정답이다.

필수값은 compose 에서 ${VAR:?메시지} 로 묶어 빠지면 기동을 멈추게 했다. 조용히 반쯤 망가지는 것보다 낫다.

이 과정에서 찾은 기존 버그 둘

compose 가 NAVER_CLIENT_ID 를 넘기고 있었는데 코드가 읽는 키는 naver.search.client-id 였다. 이름이 안 맞아서 도커로 띄우면 네이버 뉴스 검색이 조용히 죽는 구조였다. NAVER_SEARCH_CLIENT_ID 로 정정했다.

빈 문자열도 오버라이드다. application.yml 에 dart.api-key: ${DART_API_KEY:} 가 있어서, 환경변수가 비어 있으면 빈 문자열이 secret 파일 값을 덮어쓴다. .env 에 DART_API_KEY= 로 두면 DART 공시가 죽는다. compose 의 주석에는 "비워두면 application-secret.yml 의 기본값이 쓰인다"고 적혀 있었는데 사실이 아니었다.

삽질 하나

.env 를 채우려고 application-secret.yml 에서 값을 복사했는데, 그 파일이 값을 Spring 플레이스홀더 형태로 적어 두고 있었다.

kis:
  app-key: ${KIS_APP_KEY:실제값}   # 환경변수 있으면 그걸, 없으면 실제값

Spring 입장에선 잘 만든 설정이다. 그런데 이 문자열을 그대로 .env 에 넣으니 compose 가 죽었다.

failed to read .env: Invalid template: "${KIS_APP_KEY:PSsG...}"

compose 는 ${VAR:-기본값} 과 ${VAR:?메시지} 만 알고 ${VAR:기본값} 은 모른다. 7개 키가 같은 상태였다. 값을 옮길 때는 껍데기를 벗겨야 한다.

그리고 .env 백업본을 만들었더니 .gitignore 가 .env 만 막고 있어서 .env.bak-2026-09-04 는 커밋 대상이었다. 범위를 넓혔다.

.env
.env.*
!.env.example

6. MySQL 이 두 개가 되는 사고

로컬 배포에서 제일 조심해야 할 지점이다. 이 구성에는 MySQL 이 두 개 존재할 수 있다.

컨테이너 안의 3306 과 윈도우의 3306 은 완전히 다른 포트다. 컨테이너마다 네트워크 네임스페이스가 따로 있으니 충돌이 없다. 3307 을 쓰는 이유도 격리 때문이 아니라 윈도우의 3306 이 이미 로컬 MySQL 에 점유돼 있어서 호스트 쪽 문 번호를 비켜준 것뿐이다.

문제는 포트 충돌이 아니라 어느 MySQL 에 닿느냐다. 둘 다 자기 기준에서는 3306 이라 이름만 보면 구분이 안 된다.

실행 위치localhost:3306 이 가리키는 곳
컨테이너 안 (backend, batch)컨테이너 DB
윈도우에서 직접 (python run_pipeline.py)윈도우 MySQL

krx 파이프라인의 db_config.py 는 krx/.env 를 읽고 기본값이 localhost:3306 이다. 백엔드는 컨테이너 DB 를 보는데 krx 를 호스트에서 돌리면 윈도우 DB 에 쌓인다. 에러가 안 나고 조용히 어긋난다. 수집한 데이터가 화면에 안 나오는데 로그에는 성공이라고 찍히는 상황이 되는 것이다.

해법은 파이프라인도 compose 로 돌리는 것이다. batch 프로파일은 평소엔 안 뜨고 필요할 때만 일회성으로 실행한다.

docker compose run --rm batch python run_pipeline.py --only domestic,nasdaq

이러면 compose 가 DB_HOST=mysql, DB_PORT=3306 을 주입하므로 krx/.env 의 값이 무시되고 포트 혼동이 원천적으로 사라진다. up 이 아니라 run --rm 인 게 중요하다. 배치는 상시 서버가 아니라서 up 으로 띄우면 기본 명령만 돌고 Exited 로 남는다.

배치 컨테이너에는 data/ 를 볼륨으로 마운트해야 한다. 파이프라인이 여기에 캐시를 쓰기 때문이다(nasdaq100_cache.txt, nasdaqtraded_cache.txt, us_exchange_universe.json). 외부 API 가 실패하면 마지막 성공본으로 폴백하는 안전장치인데, --rm 으로 돌리면 컨테이너와 함께 사라져서 그 폴백이 매번 비어 있게 된다.

이 이미지에는 torch 가 없다. 감성 모델 재학습, ONNX export, 변곡점 모델 학습은 계속 conda 환경에서 GPU 로 한다. 수집 단계만 컨테이너에서 돈다. 뉴스 감성 추론은 백엔드가 ONNX 로 하므로 배치에 torch 가 필요 없다.

그리고 이 사실을 채팅에만 두면 잊는다. compose 머리말, krx/Dockerfile, krx/.env.example 세 곳에 경고를 박아 뒀다.

7. 덤프 이관에서 PowerShell 3연타

컨테이너 MySQL 은 빈 DB 로 시작하니 1.69GB 를 옮겨야 한다. 여기서 PowerShell 에 세 번 걸렸다.

하나. > 리다이렉션이 UTF-16 으로 쓴다. mysqldump ... > dump.sql 로 받으면 파일이 UTF-16 이 되어 깨진다. 2편에서 파이썬 로그로 같은 데 걸렸는데 또 걸렸다. --result-file 옵션을 쓰면 mysqldump 가 파일에 직접 쓰므로 셸을 안 거친다.

mysqldump -u root -p --single-transaction --routines --default-character-set=utf8mb4 --result-file=D:\git\dump.sql stock_information_backend

둘. PowerShell 은 < 입력 리다이렉션을 아예 지원하지 않는다. "연산자는 나중에 사용하도록 예약되어 있습니다"가 뜬다. cmd 로 전환하거나 cmd /c "..." 로 감싸야 한다. Get-Content dump.sql | docker ... 방식은 1.7GB 를 줄 단위로 읽으며 인코딩을 다시 씌우기 때문에 쓰면 안 된다.

셋. < 로 stdin 이 파일이면 mysql 이 비밀번호를 물어볼 수 없다. -p 뒤에 붙여 써야 한다.

docker compose exec -T mysql mysql -u root -p비밀번호 --default-character-set=utf8mb4 stock_information_backend < D:\git\dump.sql

Using a password on the command line interface can be insecure 는 에러가 아니라 경고다.

순서도 중요하다. MySQL 컨테이너만 먼저 띄우고 넣은 다음 나머지를 올린다. 백엔드를 같이 띄우면 ddl-auto: update 가 빈 테이블을 먼저 만들어 import 와 엉킨다. mysqldump 에 DROP TABLE IF EXISTS 가 들어 있어서 결과적으로는 덮어쓰지만, 순서를 지키는 편이 깔끔하다.

1.7GB 는 15~40분 걸린다. 진행 표시가 없어서 멈춘 것처럼 보이는데, 다른 터미널에서 확인할 수 있다.

docker compose exec mysql mysql -u root -p비번 -e "SELECT table_name, table_rows FROM information_schema.tables WHERE table_schema='stock_information_backend' ORDER BY data_length DESC LIMIT 8;" stock_information_backend

행을 넣을 때마다 보조 인덱스를 갱신하고 복원은 단일 스레드라 CPU 코어를 하나만 쓴다. 그래서 파일 크기에 비해 오래 걸린다.

8. 공개 전 점검

네트워크 계층은 터널이 막아 준다. 애플리케이션은 별개다. SecurityConfig 를 다시 읽어 보니 공개하면 문제가 될 자리가 있었다.

/api/v1/kis/** 가 인증 없이 열려 있었다. 한국투자증권 API 로 나가는 경로인데 KIS 는 호출제한이 있다. 반복 호출로 내 계정의 쿼터를 남이 소진시킬 수 있다. 코드에 KisRateLimiter 가 있긴 한데 그건 KIS 쪽 제한을 안 넘기려는 자체 제어지 방문자별 스로틀링이 아니다.

AI 가격예측도 열려 있었다. 종목당 2,600개 시퀀스를 ONNX 모델 3개에 한 번에 밀어넣는 연산이다. Redis 가 종목·날짜별로 캐시하니 같은 종목 반복은 싸지만, 종목을 바꿔가며 부르면 캐시 미스마다 추론이 돈다.

두 겹으로 막았다. 애플리케이션에서는 신호 관련 GET 을 전부 회원 전용으로 돌렸다.

.requestMatchers(HttpMethod.GET, "/api/v1/stocknews", "/api/v1/stocknews/**").authenticated()

이 규칙이 PUBLIC_GET_ENDPOINTS 의 permitAll 보다 먼저 와야 한다. Spring Security 는 먼저 걸리는 규칙이 이긴다. 수집용 POST /api/v1/stocknews 는 X-Batch-Key 로 따로 검증하므로 그대로 열어 뒀다.

앞단에서는 Cloudflare Rate limiting 규칙을 걸었다. 무료 플랜에서 규칙 하나를 쓸 수 있다. /api/v1/kis/ 와 /api/v1/stocknews/predict 를 같은 IP 기준 1분에 10요청으로 묶고 초과하면 10분 차단이다.

다만 화면 단위로 회원 제한을 걸어도 API 를 다 잠글 수는 없다는 걸 알게 됐다. 종목 상세 페이지를 공개로 두는 한, 그 페이지가 쓰는 /news/by-ticker, /short-sale, /opinions, /options, /disclosures, /macro 는 전부 열려 있어야 한다. 뉴스 페이지를 회원 전용으로 돌려도 홈의 최신뉴스가 /news/search 를 쓰니 그것도 열어야 한다. 결국 API 레벨에서 실제로 잠글 수 있었던 건 그 페이지만 쓰는 6개뿐이었다. 나머지는 프론트 라우트 가드가 실질적인 방어선이다. 공개 화면을 하나라도 남기면 피할 수 없는 구조다.

9. 남은 것

배포는 됐지만 목록이 줄어들지는 않았다.

ddl-auto 는 아직 update 다. 운영에서 Hibernate 가 스키마를 바꾸는 건 위험하니 validate 로 바꾸고 스키마 변경은 db/migration/*.sql 로만 하도록 정리해야 한다. 이번에 stock_news 에 유니크 제약을 추가하면서 마이그레이션 폴더를 만들었으니 그걸 확장하면 된다.

배포 문서에 DB 시드 실행 단계가 없다는 것도 이번에 발견했다. db/ 폴더에 종목 설명 370건과 역사적 시나리오 사건 50건이 SQL 로 들어 있는데, Flyway 도 없고 resources/ 에 data.sql 도 없어서 아무것도 자동으로 실행되지 않는다. 지금 DB 에 데이터가 있는 건 예전에 한 번 손으로 넣었기 때문이고, 새 서버에 배포하면 통째로 빈 채로 조용히 뜬다. 게다가 ScenarioEventSeeder 가 기동 시 5건을 자동으로 넣고 SQL 은 50건짜리 상위집합이라 둘이 겹친다. 시더를 지우고 SQL 을 마이그레이션으로 옮기는 게 맞다.

백업 cron 이 제일 급하다. 로컬 배포의 유일한 구조적 약점이라 mysqldump 를 작업 스케줄러에 걸어야 한다.

그리고 노출 이력이 있는 키 로테이션. 이번에도 compose 에러 메시지에 KIS 앱 키가 평문으로 찍혀 나왔다. 설정 값을 다루는 작업은 어디선가 반드시 화면에 뜬다고 가정하는 게 맞다.
