프론트엔드 빌드 도구는 왜 빨라졌나 (1) - 번들러 지도

2026.08.15 · #vite #webpack #esbuild #rolldown #번들러 #프론트엔드

이 글에 대해

"요즘은 CRA 대신 Vite를 쓴다"까지는 다들 안다. 그런데 왜 빠른지, Vite 말고 뭐가 있는지, 그것들이 서로 어떤 관계인지는 정리된 걸 보기 어렵다. 이름만 늘어놓으면 이렇다.

webpack, Vite, esbuild, SWC, Rollup, Rolldown, Parcel, Turbopack, Rspack, Rsbuild, Bun, Oxc, Biome...

이렇게 늘어놓기만 해서는 뭐가 뭔지 알 수 없다. 층이 다른 것들이 한 줄에 섞여 있기 때문이다. 그래서 두 편으로 나눈다.

  • 1편(이 글) — 빌드 도구. 소스 코드를 브라우저가 실행할 파일로 바꾸는 층. 왜 빨라졌는지를 원리에서부터 본다
  • 2편 — 메타 프레임워크. Next.js, Astro, SvelteKit처럼 렌더링 방식과 라우팅까지 정해주는 층

먼저 이 둘을 구분해야 한다.

빌드 도구메타 프레임워크
무엇을 정해주나번들링, 트랜스파일, dev 서버, HMR라우팅, 렌더링 방식(SSR/SSG), 데이터 로딩, 배포

관계아래 층위 층 — 내부에서 빌드 도구를 쓴다

Astro는 Vite 위에 얹혀 있고, Next.js는 Turbopack을 쓴다. 그러니까 "Vite와 Next.js 중에 뭘 쓸까"는 사실 성립하지 않는 질문이다. 층이 다르다.

번들러는 왜 생겼나

빠른 이유를 이해하려면 원래 뭘 하고 있었는지부터 봐야 한다.

브라우저에는 오랫동안 모듈 시스템이 없었다. <script> 태그를 순서대로 나열하고 전역 변수로 소통하던 시절이 있었고, Node의 CommonJS(require)는 브라우저에서 돌지 않았다. 그래서 **"여러 파일을 하나로 합쳐서 브라우저가 이해하는 형태로 만들어주는 도구"**가 필요했다. 그게 번들러다.

여기에 요구사항이 계속 붙었다.

  • JSX, TypeScript처럼 브라우저가 모르는 문법을 변환해야 한다 (트랜스파일)
  • 최신 문법을 구형 브라우저용으로 낮춰야 한다 (Babel, polyfill)
  • CSS, 이미지, 폰트도 import 하고 싶다 (로더)
  • 안 쓰는 코드를 지워야 한다 (트리 셰이킹)
  • 파일이 커지면 나눠서 필요할 때만 받아야 한다 (코드 스플리팅)
  • 파일을 고치면 새로고침 없이 화면에 반영돼야 한다 (HMR)

webpack이 이걸 전부 해냈다. 그래서 10년 가까이 표준이었다. 문제는 이 모든 걸 JavaScript로 하고 있었다는 것이다.

느렸던 이유 세 가지

1. 개발 서버를 띄우려고 전부 번들링했다

전통적인 번들러의 dev 서버는 이렇게 동작한다.

진입점 파일 → import 따라가며 전체 그래프 탐색
           → 전부 트랜스파일
           → 하나(또는 몇 개)의 번들로 합침
           → 그제서야 서버 시작

파일이 100개면 100개를 다 처리하고 나서야 브라우저가 첫 화면을 볼 수 있다. 프로젝트가 커질수록 시작 시간이 선형으로 늘어난다. 화면 하나만 보고 싶어도 앱 전체를 빌드해야 한다.

2. 도구 자체가 JavaScript로 쓰여 있었다

webpack도 Babel도 JavaScript다. 그리고 JavaScript는 이런 종류의 작업에 불리하다.

  • 싱글 스레드가 기본이다. 파일 100개를 병렬로 파싱하기 어렵다
  • GC가 있다. 파싱 중에 만들어지는 수많은 AST 객체가 계속 메모리를 오가며 GC를 부른다
  • JIT 워밍업이 필요하다. 짧게 끝나는 CLI 작업에서는 최적화가 붙기도 전에 끝난다

파싱과 문자열 처리를 수만 번 반복하는 작업에서 이 셋은 전부 손해다.

3. 캐시가 거칠었다

파일 하나를 고쳤을 때 다시 해야 할 일이 그 파일만이 아니었다. 의존성 그래프를 다시 계산하고, 청크를 다시 만들고, 상당 부분을 다시 처리했다. 재빌드가 초기 빌드만큼 걸리는 일이 흔했다.

빨라진 이유 ① 번들링을 안 하는 개발 서버

2020년 전후로 상황이 바뀌었다. 모든 최신 브라우저가 네이티브 ES 모듈(<script type="module">)을 지원하게 됐다. 브라우저가 스스로 import를 따라갈 수 있다면, 개발 중에 번들링을 할 이유가 없다.

Vite의 dev 서버가 이걸 한다.

[ 전통 방식 ]
전체 번들링 → 서버 시작 → 브라우저 요청 → 완성된 번들 전달
   (느림)

[ Vite 방식 ]
서버 즉시 시작 → 브라우저가 /src/main.jsx 요청
              → 그 파일만 변환해서 전달
              → 브라우저가 import 를 보고 다음 파일 요청
              → 그 파일만 변환해서 전달  ...

화면에 실제로 필요한 파일만, 요청이 들어온 순간에 변환한다. 프로젝트가 아무리 커도 dev 서버 기동 시간이 거의 일정하다. 파일 100개짜리 프로젝트에서 첫 화면에 30개만 쓴다면 30개만 처리한다.

HMR도 같은 원리로 빨라진다. 파일 하나를 고치면 그 파일 하나만 다시 변환해서 교체한다. 번들을 다시 만들 필요가 없으니 프로젝트 크기와 무관하게 즉각적이다.

그런데 의존성은 미리 번들링한다

여기서 예외가 하나 있다. node_modules는 미리 번들로 묶어둔다(dependency pre-bundling). 이유가 둘이다.

  • 요청 폭발 — lodash 같은 라이브러리는 내부 모듈이 수백 개다. 그대로 두면 브라우저가 HTTP 요청을 수백 번 날린다. 하나로 묶으면 요청 하나다
  • CommonJS 변환 — 아직 CommonJS로만 배포되는 패키지가 많다. 브라우저는 require를 모르므로 ESM으로 바꿔줘야 한다

의존성은 자주 안 바뀌므로 한 번 묶어두고 캐시한다. node_modules/.vite가 그 캐시다. 패키지를 새로 깔았는데 뭔가 이상하면 이 디렉터리를 지우거나 --force로 다시 만들면 된다.

dev와 build가 달랐던 문제

Vite의 약점이 오랫동안 여기 있었다. 개발은 번들링을 안 하는데 프로덕션 빌드는 번들링을 한다. 코드 스플리팅, 트리 셰이킹, 캐시 최적화 때문에 프로덕션에서는 여전히 번들이 필요하다.

그래서 Vite는 두 개의 다른 도구를 썼다. 개발 중 변환은 esbuild(Go), 프로덕션 빌드는 Rollup(JavaScript). 도구가 다르니 미묘한 차이가 났다. 개발에선 되는데 빌드하면 깨지는 일이 여기서 나왔다.

이 문제를 정리한 게 뒤에 나올 Rolldown이다.

빨라진 이유 ② Go와 Rust

2020년 esbuild가 등장하면서 판이 바뀌었다. Go로 쓴 번들러였고, 같은 작업을 webpack보다 10~100배 빠르게 했다. 만든 사람(Evan Wallace)이 정리한 이유는 대략 이렇다.

  • 네이티브 코드다. JIT 워밍업이 없다
  • 병렬 처리를 제대로 한다. 파싱·링크·코드 생성을 CPU 코어 수만큼 나눠서 돌린다
  • AST를 한 번만 만든다. 기존 도구 체인은 Babel이 만든 AST를 webpack이 다시 파싱하는 식으로 같은 코드를 여러 번 파싱했다
  • 메모리를 아껴 쓴다. 문자열 복사를 최소화하고 GC 압박을 줄인다

이후 흐름은 Rust로 넘어갔다. SWC, Rspack, Turbopack, Rolldown, Oxc가 전부 Rust다. Go와 달리 GC가 없어(소유권 모델) 지연이 튀지 않고, WASM 툴체인이 성숙해 브라우저·엣지에서도 같은 코드를 돌릴 수 있다는 점이 컸다.

핵심은 언어 자체가 마법이라서가 아니라, 이 작업이 원래 네이티브 언어에 유리한 종류의 작업이었다는 것이다. 파싱, 문자열 처리, 트리 순회를 수만 번 반복하는 일이다.

빨라진 이유 ③ 증분 캐시

세 번째 축은 다시 하지 않는 것이다.

Turbopack이 이 방향을 가장 밀어붙였다. 함수 호출 단위로 결과를 기억해뒀다가, 입력이 안 바뀌었으면 다시 실행하지 않는다. 파일 하나를 고치면 그 파일에서 파생되는 계산만 다시 한다.

여기에 영속 캐시가 붙는다. 캐시를 메모리에만 두면 dev 서버를 껐다 켤 때마다 처음부터 다시 한다. 디스크에 저장해두면 재시작해도 캐시가 살아 있다. Turbopack의 파일시스템 캐시(Next.js 16 기준 베타), Vite의 node_modules/.vite, webpack 5의 cache: { type: 'filesystem' }이 전부 같은 아이디어다.

이제 이름들을 제자리에 놓을 수 있다. 같은 층에 있는 것끼리만 비교하면 된다.

┌─────────────────────────────────────────────────────────┐

esbuild가 두 층에 걸쳐 있는 게 헷갈리는 지점인데, 실제로 그렇다. esbuild는 변환기이면서 번들러이기도 하다. Vite는 이 둘을 나눠 썼다 — 앱 코드에는 변환기로만, 의존성 사전 번들링에는 번들러로.

도구별로 보기

webpack — 여전히 5.x, 여전히 살아 있다

2026년 8월 기준 최신은 5.107.x다. 6은 아직 안 나왔고 로드맵 단계다.

죽은 도구는 아니다. 아직도 가장 많은 프로젝트가 이걸로 돌아가고, 로더/플러그인 생태계는 여전히 가장 두껍다. Module Federation(여러 앱이 런타임에 모듈을 주고받는 마이크로 프론트엔드 방식)처럼 다른 데는 없는 기능도 있다.

다만 새로 시작하는 프로젝트가 webpack을 고를 이유는 거의 없어졌다. 속도 차이가 크고, webpack만의 강점이던 설정·로더 생태계마저 대안들이 그대로 받아들였기 때문이다.

esbuild — Go, 아직도 0.x

2026년 8월 기준 v0.28.x. 나온 지 6년이 됐는데 아직 1.0이 아니다(만든 사람이 의도적으로 신중한 편이다).

"엄청나게 빠르지만 기능은 최소한"이라는 포지션을 유지한다. 코드 스플리팅과 CSS 처리가 Rollup만큼 정교하지 않고, 플러그인 API도 제한적이다. 그래서 최종 번들러보다는 다른 도구 안에서 변환기로 쓰이는 경우가 많다. Vitest, Angular의 빌드 시스템, 그리고 Vite 7까지의 개발 중 변환이 전부 esbuild였다.

SWC — Rust, Babel 자리를 가져갔다

Babel과 같은 일(JSX/TS 변환, 문법 낮추기, 플러그인)을 Rust로 한다. Next.js가 Babel을 걷어내고 SWC로 간 게 결정적이었고, Parcel과 Deno도 쓴다.

Babel이 완전히 죽지는 않았다. React Compiler처럼 Babel 플러그인으로만 나오는 것들이 아직 있다. Next.js도 Babel 설정이 있으면 자동으로 Babel을 켠다.

Rollup — 라이브러리 번들링의 기준

깔끔한 ESM 출력과 트리 셰이킹으로 유명하다. 오랫동안 Vite의 프로덕션 빌드를 담당했고, 지금도 4.x가 유지보수되고 있다.

애플리케이션보다 라이브러리를 배포할 때 여전히 좋은 선택이다. 출력이 사람이 읽을 수 있을 만큼 깔끔하고, es/cjs/umd 여러 포맷을 동시에 뽑기 좋다.

Vite — 그리고 Rolldown

지금 프론트엔드 빌드 도구의 기본값이다. Vue를 만든 Evan You가 시작했고, 지금은 VoidZero라는 회사가 전담 팀을 두고 개발한다.

가장 큰 변화가 Vite 8(2026년 3월)이다. esbuild + Rollup 이원 구조를 버리고 Rolldown 하나로 통합했다.

  • Rolldown — Rust로 쓴 번들러. Rollup의 플러그인 API를 그대로 채택해서 기존 플러그인이 대부분 그대로 돈다. Vite 8은 1.0 직전 버전으로 먼저 통합했고, Rolldown 1.0 자체는 2026년 5월에 나왔다
  • Oxc — Rolldown이 내부에서 쓰는 파서·변환기·minifier 툴체인. 역시 Rust
  • 공식 발표 기준 빌드가 최대 10~30배 빨라졌다고 한다. 사례로 Linear의 빌드가 46초에서 6초로 줄었다는 수치가 함께 나왔다
  • @vitejs/plugin-react v6부터는 React Refresh 변환도 Babel 대신 Oxc를 쓴다

의미가 큰 건 속도보다 dev와 build가 같은 번들러를 쓰게 됐다는 점이다. 앞에서 말한 "개발에선 되는데 빌드하면 깨진다"의 구조적 원인이 사라졌다.

Node 요구사항은 20.19+ / 22.12+다. 다만 Environment API(SSR·워커·엣지 등 여러 실행 환경을 하나의 설정으로 다루는 새 API)는 아직 완전히 stable은 아니다. 메타 프레임워크들이 이걸 기다리고 있다.

Rspack / Rsbuild — webpack 설정을 그대로 가져가고 싶다면

ByteDance가 만든 Rust 번들러. webpack의 설정과 로더·플러그인을 거의 그대로 받아들이는 것이 존재 이유다. 2026년 4월에 2.0이 나왔다.

webpack 설정 파일이 수백 줄인 오래된 프로젝트에서 가장 현실적인 탈출구다. Vite로 가려면 설정을 처음부터 다시 써야 하지만, Rspack은 webpack.config.js를 거의 그대로 두고 시작할 수 있다.

Turbopack — Next.js 안에서만

Vercel이 만든 Rust 번들러. webpack을 만든 Tobias Koppers가 참여했다.

Next.js 16부터 dev와 build 모두 stable이 됐고 기본 번들러가 됐다. 공식 수치로 프로덕션 빌드 2~5배, Fast Refresh 최대 10배 빠르다고 한다. webpack으로 돌아가려면 next build --webpack을 쓴다.

주의할 점은 아직 Next.js 밖에서 독립적으로 쓸 수 없다는 것이다. "프레임워크 독립 번들러"를 목표로 시작했지만 2026년 현재 그 단계에 도달하지 않았다. 그래서 Vite나 Rspack과 나란히 놓고 "뭘 고를까" 하는 대상이 아니다. Next.js를 고르면 딸려 오는 것에 가깝다.

Parcel — 설정 제로였지만

parcel index.html 한 줄로 끝나는 무설정 번들러였고, 아이디어가 좋았다. 다만 2026년 8월 기준 마지막 릴리스가 2025년 2월이라 활동이 눈에 띄게 줄었다. 새 프로젝트에 권하기는 어렵다.

Bun — 런타임이면서 번들러

Zig로 쓴 JavaScript 런타임인데, 패키지 매니저 + 테스트 러너 + 번들러를 한 바이너리에 다 넣었다. 2026년 8월 기준 1.4.x다.

단일 실행파일 컴파일(--compile)은 일찍부터 있었고, 1.3에서 프로덕션 빌드와 React Fast Refresh를 포함한 HMR 개발 서버가 더해졌다. 도구 개수를 줄이고 싶다면 매력적인 선택지다.

다만 생태계 성숙도는 Vite와 차이가 있다. Vite 플러그인이 그대로 돌지 않고, 오래된 Node 전용 패키지에서 호환 문제를 만날 수 있다.

곁가지: 린터와 포매터도 같은 흐름

빌드 도구는 아니지만 같은 이유로 같은 변화가 일어났다.

  • Biome — Rust. 포매터 + 린터 통합. Prettier와 97% 호환에 훨씬 빠르다고 주장한다
  • oxlint — Rust. ESLint 대비 수십 배 빠르다고 한다. Oxc 프로젝트의 일부라 Vite/Rolldown과 같은 툴체인을 공유한다

둘 다 ESLint를 완전히 대체하진 못한다. 커스텀 규칙과 플러그인 생태계가 아직 ESLint 쪽이 압도적이다. 실무에서는 빠른 린터로 대부분을 걸러내고, ESLint는 필요한 규칙만 남기는 병행 구성을 많이 쓴다.

벤치마크 숫자를 읽는 법

"10배 빠르다", "30배 빠르다" 같은 수치를 볼 때 몇 가지를 확인하는 게 좋다.

  • 누가 측정했나 — 대부분 도구를 만든 쪽이 낸 수치다. 틀렸다는 게 아니라, 자기 도구에 유리한 조건일 가능성이 높다
  • 무엇을 쟀나 — 콜드 스타트인지, HMR인지, 프로덕션 빌드인지. 세 숫자는 서로 다르고 개선 폭도 다르다
  • 어떤 프로젝트인가 — 파일 100개짜리와 10,000개짜리는 결과가 완전히 다르다. 작은 프로젝트에서는 어느 도구를 써도 체감 차이가 없다
  • 무엇과 비교했나 — "webpack 대비"인지 "이전 버전 대비"인지

그리고 정말 중요한 건 총 빌드 시간이 아니라 HMR 지연이다. 하루에 프로덕션 빌드는 몇 번 돌리지만, 파일 저장은 수백 번 한다. 저장하고 화면이 바뀌기까지 200ms인지 3초인지가 실제 생산성을 가른다.

가장 정확한 벤치마크는 내 프로젝트에서 직접 재보는 것이다.

# dev 서버 콜드 스타트
rm -rf node_modules/.vite && time npx vite --port 5199 &
# HMR 은 브라우저 콘솔의 [vite] hot updated 로그 타임스탬프로 확인

# 프로덕션 빌드 (캐시 없이)
rm -rf node_modules/.vite dist && time npm run build

CRA는 왜 사라졌나

create-react-app은 2025년에 공식적으로 deprecated 됐다. 지금 React 공식 문서는 CRA를 "더 이상 권하지 않는 것"으로만 언급하고, 새 프로젝트 안내에서는 완전히 빠졌다.

이유는 속도만이 아니었다.

  • 관리가 멈췄다. react-scripts가 물고 있는 webpack 4/5 계열 의존성 때문에 설치할 때마다 취약점 경고가 쏟아졌다
  • 설정을 못 건드린다. eject 아니면 craco 같은 우회로가 필요했다
  • SSR도, 라우팅도, 데이터 로딩도 없었다. 실제 앱에는 결국 다 필요한 것들이다

지금 React 공식 문서가 권하는 순서는 이렇다.

  1. 프레임워크를 먼저 고른다 — Next.js, React Router v7, Expo(네이티브)
  2. 프레임워크가 필요 없다면 Vite / Rsbuild / Parcel로 직접 구성한다

두 번째가 명백히 비주류 취급이라는 게 흥미로운 지점이다. 왜 React 팀이 "프레임워크 먼저"라고 말하게 됐는지가 2편의 주제다.

정리

  • 빌드 도구와 메타 프레임워크는 층이 다르다. Vite와 Next.js는 비교 대상이 아니다
  • 느렸던 이유는 셋이었다 — 전부 번들링하고 시작, JS로 쓰인 도구, 거친 캐시
  • 빨라진 이유도 셋이다 — 네이티브 ESM 개발 서버, Go/Rust 툴체인, 증분·영속 캐시
  • Vite의 dev 서버는 필요한 파일만 그때그때 변환한다. 그래서 프로젝트 크기와 무관하게 빠르다
  • 의존성만은 미리 번들링한다(요청 폭발 + CommonJS 변환)
  • Vite 8부터 esbuild + Rollup이 Rolldown 하나로 통합됐다. dev와 build가 같은 번들러를 쓴다
  • Turbopack은 Next.js 안에서만 쓴다. 독립 도구가 아니다
  • webpack 레거시의 현실적인 탈출구는 Rspack이다
  • 벤치마크는 총 빌드 시간보다 HMR 지연을 본다. 그리고 내 프로젝트에서 직접 잰다
  • CRA는 끝났고, React는 이제 "프레임워크를 먼저 고르라"고 말한다

다음 편에서는 그 프레임워크들 — Next.js, Nuxt, SvelteKit, Astro가 무엇을 다르게 하는지, 렌더링 방식이라는 축으로 정리한다.
