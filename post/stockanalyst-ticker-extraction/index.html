StockAnalyst 뉴스에서 종목 뽑아내기 - Gemini 대신 사전 매칭으로

2026.09.01 · #python #정규식 #뉴스 #종목추출 #stockanalyst

StockAnalyst는 Spring Boot + React(Vite) + Python 파이프라인으로 만든 주식 정보 서비스다. 시세와 뉴스, 포트폴리오, 위험분석을 한 화면에서 보여주고, 데이터 파이프라인은 Python으로 돌린다. 이 글은 그중 뉴스 기사에 관련 종목을 붙이는 기능을 다시 만든 기록이다. 같은 기사에 호재/악재 점수를 붙이는 쪽은 감성 모델 글에 따로 정리했다. 이후 작업 전체의 목차는 개발기 (2)에 있다.

한눈에 보기

  • 종목 추출은 LLM 대신 종목명 사전 + 정규식으로. 기사 한 건에 1ms, 환각 0건
  • 한국어는 조사가 바로 붙어서 \b가 안 통한다 → 뒤 글자가 조사일 때만 통과시키는 경계 규칙
  • 본문에서만 잡힌 종목은 44%가 노이즈라 제목에 나온 종목만 연결
  • 중복 기사는 글자 2-gram + 오버랩 계수로 걸러서 DB의 21%를 정리

왜 바꿨나

처음엔 Gemini API 한 번 호출로 두 가지를 같이 처리했다. 기사 제목과 본문을 넣으면 "이 기사는 호재인가 악재인가"와 "어느 종목 얘기인가"를 한 번에 돌려줬다. 편했다. 문제는 세 가지였다.

문제증상
호출 제한검색어당 100건 × 수십 개 검색어 = 하루 수천 건. 중간에 429가 나면 그날 수집은 반쪽
실시간 불가사용자가 검색할 때마다 LLM 호출은 응답 시간으로도 비용으로도 말이 안 된다
환각기사에 없는 종목을 붙이거나, "SK오션플랜트"를 엉뚱한 종목 코드로 연결

셋 중 환각이 제일 아팠다. 종목 코드는 틀리면 바로 티가 나는 값이다.

그래서 두 문제를 성격에 맞게 갈랐다. 종목 추출은 "기사에 실제로 있는 이름만 잡는" 결정론적 방식으로, 감성은 따로 학습한 작은 분류 모델로. 이 글은 앞쪽 얘기다.

1. 기본 아이디어 - 사전과 정규식

DB의 stock 테이블에는 국내외 종목의 name과 kor_name이 있다. 이걸 전부 모아서 하나의 정규식 alternation(삼성전자|SK하이닉스|현대차|...)으로 만들고 기사 제목과 본문에서 찾는다. 모델도 외부 호출도 없으니 기사 한 건 처리에 1ms도 안 걸리고, 사전에 없는 종목이 튀어나올 일이 없다.

긴 이름부터 정렬해야 하는 이유

alternation을 만들 때 이름을 길이 내림차순으로 정렬하는 게 첫 번째 규칙이다. 정규식 엔진은 A|B에서 "가장 긴 쪽"이 아니라 "먼저 적힌 쪽"을 시도하고, 성공하면 거기서 멈춘다.

패턴 순서입력 "삼성전자우 급등"결과
삼성전자|삼성전자우삼성전자가 먼저 성공 → 멈춤삼성전자 (틀림)
삼성전자우|삼성전자삼성전자우 먼저 시도 → 성공삼성전자우 (맞음)

LG|LG전자|LG화학도 같은 문제다. 긴 것부터 적어 두면 엔진이 긴 이름을 먼저 시도하고, 실패했을 때만 짧은 이름으로 내려온다.

사전 세 겹

stock 테이블 이름만으로는 부족해서 사전을 세 겹 더 얹었다.

사전예이유
약칭 ALIAS_EXTRA아모레, LG생건, 금호석화, 한화에어로, SKT, 모비스, 엔씨, 카뱅, 두산에너빌, KAI기사는 정식 명칭을 거의 안 쓴다. "아모레퍼시픽"보다 "아모레"가 훨씬 많다
1:N 별칭 MULTI_ALIAS삼전닉스 → 005930 + 000660, 반도체 투톱 → 005930 + 000660, 하닉 → 000660한 단어가 두 종목을 가리키는 관용 표현. 별칭 하나가 코드 여러 개로 펼쳐진다
미국 종목 한글명 US_NAME엔비디아 → NVDA, 브로드컴 → AVGO, 홈디포 → HD (약 60개)미국 종목은 한국 기사에 한글로만 나온다. NVIDIA로는 국내 기사가 안 잡힌다

세 겹 다 결국 "문자열 → 종목 코드 목록" 맵이고, 매칭 로직은 하나다. 사전만 갈아 끼우면 된다.

2. 한국어라서 생기는 문제 - 조사 경계

여기가 첫 번째로 오래 걸린 부분이다.

영어의 \b가 한국어에서 안 되는 이유

영어라면 \b(단어 경계)로 끝난다. \bApple\b은 "Apple"은 잡고 "Applesauce"는 안 잡는다. \b는 "단어 문자와 단어가 아닌 문자 사이"를 뜻하는데, 영어는 단어 사이에 항상 공백이 있으니 이게 곧 단어 경계다.

한국어는 종목명 뒤에 조사가 띄어쓰기 없이 바로 붙는다. "삼성전자가", "삼성전자를", "삼성전자에서는". 정규식 엔진 입장에서 한글은 전부 단어 문자라서 "삼성전자"와 "가" 사이에 경계가 없다. \b삼성전자\b는 "삼성전자가 발표했다"에서 아무것도 못 잡는다.

그렇다고 "뒤에 한글이 와도 무조건 허용"으로 풀면 반대 문제가 터진다. "하이브"가 "하이브리드"에, "신스틸"이 "신스틸러"에 걸린다. 자동차 기사마다 하이브(엔터테인먼트)가 붙는 걸 보고 알았다.

규칙 - 앞은 막고, 뒤는 조사만 열어 둔다

위치글자판정예
이름 앞한글✕ 매칭 안 함한국투자증권 → "투자증권" 부분 매칭 방지
이름 앞공백·문장 시작·기호·영문○"..., 삼성전자는"
이름 뒤한글이 아님○"삼성전자 3분기", "삼성전자(005930)"
이름 뒤한글 + JOSA_HEAD에 있음○삼성전자가, 현대차그룹
이름 뒤한글 + JOSA_HEAD에 없음✕하이브리드, 신스틸러

앞쪽은 단순하다. 앞에는 조사가 붙을 일이 없으니 한글이면 무조건 막는다. 뒤쪽이 핵심인데, "그 글자가 조사(또는 조사처럼 붙는 글자)인가"만 본다.

JOSA_HEAD = (
    "가이은는을를에의와과도로으만부까나라서보처등및요야지여며든게대마뿐조밖커토했하한된될인입니"
    + "그측주株계노사"
)

앞부분은 조사의 첫 글자들이다. "가/이/은/는/을/를/에/의/와/과/도/로/으(로)/만/부(터)/까(지)/처(럼)/등/및...". 중간의 "했/하/한/된/될/인/입/니"는 조사는 아니지만 "현대차인가", "카카오입니다", "삼성전자하고"처럼 서술어가 바로 붙는 경우를 위한 것이다.

뒤에 따로 붙인 그측주株계노사는 "현대차그룹", "삼성측", "삼성주", "LG계열", "삼성노조", "현대차사" 같은 표현 때문에 하나씩 늘어난 것이다. 자동으로 만든 목록이 아니다. dry-run을 돌려서 "잡혀야 하는데 안 잡힌 것"을 보면서 한 글자씩 추가했다.

정규식으로 옮기면

# (?<![가-힣])   앞 글자가 한글이면 실패 (부정 후방 탐색)
# (?![가-힣])    뒤 글자가 한글이 아니면 통과 (부정 전방 탐색)
# (?=[JOSA])     한글이면 JOSA_HEAD 중 하나여야 통과 (긍정 전방 탐색)
pattern = re.compile(
    r"(?<![가-힣])(" + "|".join(map(re.escape, names_longest_first)) + r")"
    r"(?:(?![가-힣])|(?=[" + JOSA_HEAD + r"]))"
)

세 가지 "탐색"은 전부 글자를 소비하지 않고 조건만 검사한다. 그래서 조사 자체는 매칭 결과에 포함되지 않고 종목명만 깔끔하게 나온다. (?<!...)는 "바로 앞이 이게 아니어야", (?!...)는 "바로 뒤가 이게 아니어야", (?=...)는 "바로 뒤가 이거여야"다.

이 규칙이 완벽하진 않다. 조사 목록에 있는 글자가 우연히 다른 단어의 첫 글자인 경우는 원리상 통과한다. 그래서 목록에 한 글자 넣을 때마다 dry-run으로 오탐이 늘지 않는지 같이 봤다.

3. 오탐을 잡기 위한 규칙들

규칙을 만든 뒤 기존 기사 2,141건에 돌려 보니 빈도 상위에 이상한 종목이 올라왔다. 하나씩 규칙이 됐다.

문제규칙효과
"나스닥"이 나스닥 거래소(NDAQ)에 32건BLOCK_NAMES - 코스피, 다우, S&P, 대만 반도체 등 지수·시장 이름 차단지수 기사에 거래소 종목이 붙는 일이 사라짐
"LS증권 김OO 연구원은..." 같은 출처 언급TITLE_ONLY_CODES + 이름에 "증권"/"금융투자"가 있으면 자동 적용. 제목에 나올 때만 연결출처로만 언급된 언론사·증권사가 관련 종목으로 붙던 문제 해결
"[헤드라인]", "이 시각 주요뉴스" 같은 모아보기제목이 이 패턴이면 본문을 아예 안 봄기사 하나에 종목 스무 개 붙는 일 방지
본문에서만 잡힌 종목의 44%가 노이즈TITLE_ONLY_TICKERS=1 - 제목에 나온 종목만 연결아래 참고

본문 매칭을 끈 근거

결정적인 건 마지막 줄이다. 본문에서만 잡힌 종목 220건을 하나씩 확인했더니 이랬다.

붙인 것의 44%가 틀린 연결이면 안 붙이는 게 낫다. 그래서 운영은 제목에 나온 종목만 연결한다.

이건 정밀도와 재현율의 교환이다. 정밀도는 "붙인 것 중 맞는 비율", 재현율은 "붙였어야 하는 것 중 실제로 붙인 비율"이다. 본문 매칭을 끄면 재현율은 조금 떨어지지만(본문에서만 언급된 종목을 놓친다) 정밀도가 크게 오른다. "이 기사는 이 종목 얘기다"라는 의미를 생각하면 제목에 없는 종목은 원래 그 기사의 주인공이 아니니, 이 교환은 남는 장사다. 본문 매칭 로직은 남겨 두고 플래그로 끈 거라, 나중에 "언급된 종목"이라는 별도 개념이 필요해지면 다시 켤 수 있다.

4. 검색어에 "주가" 붙이기

수집 쪽에서 생긴 문제다. 미국 종목을 한글 이름으로 검색하면 엉뚱한 게 온다. "애플"로 검색하면 과즙세연이 나오고, "테슬라"로 검색하면 헬로카봇이 나온다. 종목명이 일반 명사거나 다른 고유명사와 겹치는 경우다.

종목 검색어에는 전부 " 주가"를 접미로 붙였다(TICKER_QUERY_SUFFIX). "애플 주가"로 검색하면 과즙은 안 온다. 기사를 저장할 때 검색어를 태그로 남기는데, 이때는 접미를 떼서 원래 이름만 남긴다. 태그에 "애플 주가"가 찍히면 보기 흉하다.

5. 중복 기사 제거

같은 사건을 열 군데 언론사가 쓰면 제목이 조금씩 다른 기사가 열 건 쌓인다. 현대차 부사장 영입 기사가 66건 들어온 걸 보고 중복 제거를 넣었다.

어절 자카드는 왜 실패했나

처음엔 제목을 띄어쓰기로 쪼개서(어절 단위) 자카드 유사도를 구했다. 자카드는 |A ∩ B| / |A ∪ B|, 두 집합이 겹치는 비율이다. 그런데 "공급계약"과 "공급 계약"이 다른 토큰이 된다. 한국어 띄어쓰기는 언론사마다 제각각이라 같은 제목이 다르게 쪼개지고, 유사도가 뚝 떨어진다. 어절 단위는 버렸다.

글자 2-gram + 오버랩 계수

글자 2-gram 집합으로 바꿨다. 2-gram은 연속한 두 글자 묶음이다. "공급계약"은 {공급, 급계, 계약}이 되고, "공급 계약"도 공백을 빼면 같은 집합이다. 띄어쓰기 차이에 강하고, 조사 하나 바뀌는 정도는 2-gram 한두 개 차이로 끝난다.

유사도는 자카드 대신 오버랩 계수 |A ∩ B| / min(|A|, |B|)를 썼다. 분모를 합집합이 아니라 작은 쪽 집합 크기로 두는 이유는, 짧은 제목이 긴 제목에 포함되는 경우를 잡기 위해서다.

짧은 제목 A의 2-gram이 8개, 긴 제목 B가 20개, 교집합이 7개라고 하자. A의 내용은 거의 전부 B 안에 들어 있다.

지표계산값판정 (임계 0.55)
자카드7 / (8 + 20 − 7)0.33다른 기사
오버랩 계수7 / min(8, 20)0.88같은 기사

긴 제목 쪽이 붙인 수식어("글로벌 경쟁력 강화 위해...") 때문에 자카드는 낮게 나오지만, 실제로는 같은 사건이다. 오버랩 계수는 "작은 쪽이 큰 쪽에 얼마나 담겨 있나"를 보기 때문에 이걸 잡는다.

임계값은 0.55. 최근 3일치 제목과 비교해서 넘으면 저장하지 않는다. 비교 범위를 두는 이유는, 너무 오래된 기사까지 비교하면 "삼성전자, 신제품 출시"처럼 주기적으로 반복되는 제목이 다른 사건인데도 중복으로 잡히기 때문이다.
